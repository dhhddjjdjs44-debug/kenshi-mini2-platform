## 1. Что пользователь на самом деле хочет

Doom — тестовый полигон. Нужна переиспользуемая платформа, поверх которой пользователь сможет начать свою игру, не разбирая заново LCD, кнопки, звук, мотор и тактирование.
Не тратить весь срок на FPS Doom, декоративную диагностику или большой «идеальный движок».
Разделять: **драйверы/HAL → общий игровой runtime → приложения**. Doom — одно из приложений.

Приоритеты следующей рабочей сессии:
1. Независимый от Doom каркас игры и воспроизводимая сборка.
2. Реальный звук и вибро, доказательные данные о частоте CPU.
3. Проверенные кнопки, устойчивый вывод/чтение карты и понятная передача SDK пользователю.

## 3. Что значит «платформа готова к началу моей игры»

Минимальная приёмка, а не громкое название:
- Есть публичный C99 API с версией и описанием владения буферами, времени жизни объектов, ошибок и ограничений.
- Пример собственной игры собирается одной документированной командой, **не линкует Doom/PureDOOM**, рисует, двигается по кнопкам, использует время и читает свой тестовый ресурс.
- Пользователь меняет игровую логику/ресурсы, не редактируя MMIO, драйверы или загрузчик для каждой новой механики. Пока упаковка требует парного loader/ELF, это явно документировано, не выдаётся за свободный загрузчик приложений.
- Runtime отделяет update от present, не блокирует всё приложение ожиданием аудио/вибро, не пишет framebuffer во время владения DMA.
- Пример работает на телефоне; выполнен целевой непрерывный прогон хотя бы 15 минут с экраном, вводом, чтением ресурса и проверенными периферийными функциями. Время прогона — критерий приёмки, пока не достигнутый результат.
- Выводятся реальные статусы возможностей: unsupported / implemented-unverified / hardware-verified / failed. Успешное чтение регистра не превращается в hardware-verified.
- Для полной аппаратной приёмки: слышимый PCM, физический импульс мотора, отчёт о CPU с источником/делителями/основанием вывода. Неподтверждённое MHz показывать как UNKNOWN, не как 260.

Если звук/мотор к сроку не подтверждены, допустимо передать рабочий SDK, чтобы пользователь начал gameplay, **но назвать его «SDK с незакрытыми драйверами», а не полностью готовой платформой**. Перечислить конкретный остаток работ.

## 4. Порядок работы по возвращении пользователя

### Шаг A — быстро восстановить состояние, не переписывать всё

Прочитать свежие указатели и обязательные инструкции. Проверить запечатанные основы разрешённым read-only аудитом.
Создать отдельную новую рабочую копию по существующей процедуре, сохранив происхождение и контрольные суммы. Не удалять seal в оригинале.
Составить короткую таблицу: функция → текущий исходник → переиспользуемая часть → аппаратный статус.
Не разгонять и не включать новые периферийные блоки одновременно с переносом архитектуры.

### Шаг B — независимый runtime и пример

Зафиксировать небольшой API, затем сразу собрать работающий пример, а не писать большую спецификацию:
- lifecycle: init / update / render / shutdown;
- video: формат/размер, acquire / present / busy, полный безопасный fallback;
- input: raw-state отдельно, логические кнопки, pressed/released, проверенные комбинации;
- time: монотонное время и корректная обработка переполнения, update не зависит от FPS;
- assets: чтение с границами и явными ошибками; для MVP достаточно read-only, запись сохранений отдельно;
- memory: явные пределы, ошибки выделения, карта линковки/контроль стека;
- audio: оговорённый PCM-формат, очередь/обслуживание, mute/stop и счётчик underrun;
- haptics: ограниченный по времени импульс, автоматическое выключение, cancel;
- diagnostics/capabilities: доказанность функций, тайминги, сведения о тактировании.

Это целевой контракт, а не утверждение, что функции уже реализованы. Имена/сигнатуры выбрать после просмотра текущих драйверов.
Игровой API не должен требовать WAD-структур или вызывать kenshi_doom_*.
Существующий WAD ABI изолировать адаптером совместимости. Выбрать минимально рискованный путь к собственным ресурсам: проверенное расширение контракта/переиспользование чтения в RAM. До выбора не обещать произвольные файлы через старый WAD callback.
Загрузчик трогать только для необходимого и после проверки размера/пинов; не затевать универсальный launcher к сроку.
Doom переносить на тот же API поэтапно, не переписывать его ядро. Пример обязан быть независимым даже до завершения адаптации Doom.

### Шаг C — один диагностический RAM-пакет, последовательные проверки железа

В подготовленном приложении сделать понятные отдельные режимы CPU / motor / audio / keys / display / storage.
Объединить подготовку ради меньшего числа переподключений, но менять и проверять по одному аппаратному фактору. После неудачи — анализ, не автоматическое повторение записи.
Пока пользователь не подтвердил подключение, выполнять офлайн-код/модельные проверки; не ждать аппаратной готовности для всей разработки.

**CPU: сначала выяснить, потом менять.**
Снять полную относящуюся к ARM цепочку источника PLL, mux и делителей, сопоставить с архивным stock-путём. Отдельно маркировать документально декодированную, вычисленную и независимо измеренную величину.
26 MHz у GPT не считать частотой ARM. TCM benchmark ticks не переводить в MHz без обоснованного числа тактов и учёта влияния кэша/памяти.
Если цепочку пока нельзя достоверно декодировать, сохранить сырые данные и честный UNKNOWN; benchmark — только относительная производительность.
Штатные B621/PLL1401/DIV0 уже воспроизведены из stock. Не вызывать живьём полную stock-инициализацию PLL/SFI и не повышать напряжения вслепую. 100 ms — задержка, не +100 MHz.
Проверка 260 MHz — отдельный gated эксперимент только после установления текущего режима и безопасной последовательности. Не делать обещанные 260 условием старта игровой логики.

**Вибро: физический результат, не VIB1.**
Во время необходимого stock-этапа попросить проверить вибрацию с аккумулятором. Если в stock мотор не работает/режим не найден, не объявлять мотор исправным.
Разобрать реальную последовательность управления/питания. Перенести короткий ограниченный импульс с восстановлением состояния, затем неблокирующий API с автоотключением и тестом cancel.
Существующий probe `0xA07001B0` и его readback — исследовательский код, не подтверждённый драйвер. Не увеличивать напряжение наугад.

**Аудио: динамик → поток → игра.**
Сначала проверить слышимый звук в stock с аккумулятором при том же аппаратном этапе.
Просмотреть цепочку analog power/усилитель + digital PCM/интерфейс/DMA/IRQ в reference и stock. Reference AFE не считать полным готовым sink для нашей платы.
Первый аппаратный результат — короткий тихий тон с ограничением времени и корректным выключением. Потом непрерывный PCM и обработка underrun/stop без зависания кадров. Потом звуковой ресурс независимого примера и Doom SFX через общий API.
Пока нет hardware sink, наличие ненулевого PCM не считать звуком телефона. Музыка и сложные форматы не нужны для MVP.

Ограничитель распыления: если очередная рабочая итерация не даёт нового доказательства, записать конкретный неизвестный узел и следующий различающий тест. Не строить десятки новых версий ради номеров. Объём аппаратного reverse engineering до результата заранее неизвестен.

### Шаг D — ввод и устойчивость, затем передача SDK

В диагностике показать сырую матрицу и подписывать нажимаемые физические кнопки вместе с пользователем. Проверить удержание, отпускание и нужные игре одновременные нажатия, убрать утечки диагностических chord в игру.
Проверить полный и частичный LCD, DMA ownership и кэш; неподтверждённый частичный V12-режим не делать единственным вариантом SDK.
Проверить длительное чтение собственных ресурсов и Doom без маскирующих бесконечных retry; отдельно исследовать ED08.
Собрать краткую инструкцию: одна команда сборки, где менять update/render, формат ресурсов, ограничения, текущая раскладка, установка и режим диагностики.

## 5. Аппаратная дисциплина — ускорять подготовку, не рисковать чужими данными

Перед любыми операциями с телефоном прочитать актуальные:

и `C:\Users\USER\Documents\Codex\2026-11-16\senior-embedded-c99-developer-reverse-engineer\PHONE_OPERATION_RU.md`.

Пользователь ранее разрешил эксперименты и не хочет повторных общих вопросов «разрешаешь?». Это не подтверждает нынешнее подключение/режим телефона.
При необходимости спросить только нужное физическое действие, одной короткой фразой.
Действующие пределы: NOR только `[0xB000,0xF000)`, сектора 11–14; никакого full restore.
Каждая запись — новый одноразовый writer, без SPENT/retry/reset/FINISH/reconnect/clear-halt/автоотката.
Перед записью — геометрия и свежий полный 4-MiB read в той же сессии, независимая проверка pinned baseline; после — полный read, bytewise outer audit и PT_LOAD audit.
Stock может менять NV: после его запуска нужна новая read-only база с проверкой, не silent repin.
Карту заново идентифицировать, не доверять старой букве. Менять только согласованный ELF, Flush(true), close/reopen/fullhash; WAD сохранять. Диски ноутбука не форматировать и не менять. Сейчас форматирование вообще не нужно.
Новые драйверы не устанавливать автоматически только потому, что офлайн-тесты PASS.

## 6. Что отложить ради срока

Не делать редактор, полноценный 3D-движок, JIT/скриптовый язык, универсальный менеджер приложений, запись FAT, сетевой стек, поддержку множества звуковых форматов и гарантированные 60 FPS во всех играх.
Не путать FPS вывода с частотой симуляции: у Doom V12 симуляция 35 Hz, интерполяции нет.
Сначала рабочая основа и образец для начала собственной игры; дальше развивать по её реальным потребностям.

## 7. Как общаться и фиксировать результат

Коротко, по-русски, прямо. Не обещать ночную автономную работу, если она не запущена.
В конце каждого значимого этапа: что реально заработало → чем подтверждено → следующий нужный тест.
Не давать выдуманные проценты готовности и сроки на неизвестный драйвер. Не объявлять «релиз», пока критерии не проверены.
На передачу: SDK/пример/команда сборки + таблица физических подтверждений и оставшихся ограничений + актуальный путь установленной сборки.
