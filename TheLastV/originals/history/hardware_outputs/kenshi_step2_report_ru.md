# Kenshi Mini 2 / The Night Shift — шаг 2: XIP-диагностика

**Дата:** 16 ноября 2026 года.  
**Статус:** проект создан; компиляция, упаковка и офлайн-проверки выполнены. **На телефоне не запускался и не прошивался.** Это bring-up образ, а не подтверждённая рабочая прошивка и не порт игры.

## 1. Что поставлено

- Freestanding C99 + небольшой ARM startup; ISA **ARMv5TE**, ARM-режим, без Cortex-M/Thumb-2/VFP. У GCC 14.2 нет имени CPU `arm7ej-s`, поэтому используется поддерживаемый `-march=armv5te`, покрывающий нужные инструкции без Jazelle.
- `Makefile` для `arm-none-eabi-gcc`, linker script, генератор GFH, read-only извлечение board-template из проверенного дампа. Есть Python-вариант сборки для Windows без установленного GNU Make.
- Собственные reset/vector/trap-обработчики, TCM-стеки, WDT disable, remap RAM; резерв 32 КиБ кэша, PSRAM-framebuffer и 8 КиБ DMA-резерва, linker ASSERT на 2 МиБ heap.
- Диагностика полного 4-МиБ окна PSRAM, LCD ID/профили B–C–A, CPU/PIO RGB565, собственный небольшой 8×8 шрифт, цветные полосы и hex-вывод четырёх keypad-регистров и инвертированной 64-битной маски.
- Дополнительная статическая дотрассировка SD/VMC и аудио. Рабочие SD/аудио-драйверы не подменены заглушками, выдающими успех: они в этом образе **не включены**.

Структура проекта (после распаковки):

```text
kenshi_step2/
  Makefile
  README_RU.md
  requirements-test.txt
  linker/mt6261.ld
  include/{board,psram,lcd}.h
  src/startup.S
  src/{boot,board,psram,lcd,main}.c
  src/{font,lcd_profiles}.inc
  board/lcd_profiles.json
  tools/{build,extract_board,gfh,gen_lcd_profiles,check_image,check_heap_assert,fs}.py
  tests/test_packaging.py
  tests/{emulate_psram,emulate_startup}.py
  docs/                 # трассировки, свидетельства, сведения об инструментарии
  build/                # MAUI-only BIN, ELF, MAP, проверенная карта и протоколы
```

Игра не интегрирована: это отдельный аппаратный диагностический проект. Исходники The Night Shift по указанному пути дампа не предоставлены. Никакие stock MMI/RTOS/modem callbacks из новой программы не вызываются; это замена приложения, а не вырезание байтов из связанного MAUI.

## 2. Что проверено сборкой

Проверено **настоящим GCC/ld**, а не только разбором исходников:

- Arm GNU Toolchain **14.2.Rel1**, `gcc 14.2.1 20241119`; архив проверен по опубликованному SHA-256. Инструментарий размещён только в рабочем каталоге чата, не установлен глобально и не включён в архив проекта.
- Положительная сборка через Python и через **GNU Make 4.4.1**, включая принудительное пересоздание объектов (`make -B`). Предупреждения компилятора/линкера считаются ошибками. ELF: little-endian ARMv5TE; неразрешённых символов нет.
- **11/11** тестов упаковки: цепочка GFH, смещения, подпись=0, неправильный entry, повреждённый заголовок, пустой/невыровненный/слишком большой payload, логическая сохранность защищённых диапазонов и происхождение LCD-данных.
- **Отрицательный linker-тест:** добавление `0x200000` байт `.bss` действительно заканчивается ошибкой `Continuous heap smaller than 2 MiB`. Проверено требуемое ASSERT, а не произвольная ошибка инструментария.
- Исполнена **реальная скомпилированная функция `psram_test()`** в ARM-эмуляторе: 4 МиБ проходит; 2-МиБ и 1-МиБ зеркалирование обнаруживается; stuck-low bit0 обнаруживается. Зеркалирование моделируется общим backing storage, не отдельными независимыми копиями RAM.
- Отдельно выполнен startup до входа в `diagnostic_main`: первая MMIO-запись — WDT `0x2200`; banked stacks выставлены; 64 байта векторов скопированы; `.data` и `.bss` инициализированы; IRQ/FIQ остаются замаскированы.

**Граница эмуляции:** это тест инструкций и программного порядка. В startup-тесте MMIO — простая модель регистров, а cache-command искусственно auto-clear. Настоящие EMI, кэш, MPU, BL2, LCD, DMA и PMIC не эмулируются. Эти проверки **не подтверждают работу на MT6261** и не измеряют физическую RAM телефона.

## 3. Образ и GFH

| Поле | Значение |
|---|---|
| Файл | `build/kenshi_diag_maui.bin`, только замена MAUI, не полный NOR |
| Логическое смещение начала | `0x00B000` |
| Конец диапазона, не включительно | `0xd0e8` |
| Размер BIN с GFH | **8424 байт = 0x20e8** |
| load_address | `0x1000B000` |
| entry / Reset_Handler | `0x1000B5B0` |
| FILE_INFO file_type | `0x0100` |
| content_offset / jump_offset | `0x5B0` / `0x5B0` |
| signature_type / signature_length | `0` / `0` |
| max_file_size | `0x37E000` — ограничено началом системного хвоста |
| Не затрагиваемые логические диапазоны | `[0x0,0xB000)` и `[0x389000,0x400000)` |

SHA-256 подготовленного BIN:

```text
bb2bed62f7c6a83698d58a91bf276febfde13fd48a1d007703a7b0217f9c0ca6
```

Заголовок длиной `0x5B0` формируется из **ровно идентифицированного исходного dump-template**, а не выдуманной структуры. Сохраняется вся цепочка семи GFH-записей и исходная board metadata; в FILE_INFO обновляются фактическая длина и разрешённый максимум. Подпись/длины/entry проверяются, входные файлы не перезаписываются. Файл `flash-plan.json` фиксирует байтовые границы, entry и SHA-256; это **описание образа, не команда программатору**.

**Важно:** остальные GFH-записи сохранены как opaque stock metadata, включая прежние идентификационные строки и memory-related сведения. Их полная семантика в BL2 и принятие нового размера приложения **не доказаны**. Структурно корректный GFH не означает аппаратно подтверждённый handoff BL2. На этом шаге не выполнялись обход проверок, изменение ARM_BL/ARM_EXT_BL или новая подпись загрузчиков.

### Физическое стирание — отдельное обязательное условие

Границы в таблице относятся к **байтам файла**, не к erase-секторам NOR. Если конкретная NOR/программатор стирает только 64-КиБ блок, участок `0xB000` попадает в блок `[0x0,0x10000)` вместе с загрузчиками. Поэтому нельзя честно обещать «загрузчики не тронем» одной лишь упаковкой BIN. До записи нужны подтверждённые JEDEC ID, erase geometry и способ сохранения/восстановления соседних байтов; автокоманда flash/erase намеренно отсутствует. Образ не дополнен до размера всего NOR и ничего не пишет сам.

## 4. Фактическая linker-карта этого диагностического ELF

Все интервалы справа открыты. `0xF0000000+` — алиас той же PSRAM, не дополнительная память.

| Область | Физические/логические адреса | Размер / назначение |
|---|---|---|
| ARM vectors reserve | `0x00000000–0x00000100` | 256 байт; копируется `0x40` байт из `0x1000B640` |
| DMA reserve | `0x00000100–0x00002100` | `0x2000` = 8 КиБ, NOLOAD, выравнивание 32 |
| Framebuffer | `0x00002100–0x0000C100` | `0xA000` = 40 КиБ, 128×160×2, выравнивание 32 |
| `.data` | `0x0000C100–0x0000C108` | 8 байт с выравниванием; cookie проверяет копирование |
| `.bss` с выравниванием | `0x0000C108–0x0000C120` | 24 байта |
| **Непрерывный heap** | **`0x0000C120–0x00400000`** | **`0x3F3EE0` = 4 144 864 байта ≈ 3,953 МиБ** |
| TCM cache reserve | `0x70000000–0x70008000` | 32 КиБ; не используется для C-данных/стеков |
| ARM-стеки | `0x70008000–0x70009C78` | отдельные банки; SVC nominal top `0x70009C74` |
| Диагностический mailbox | `0x70009C80–0x70009CB4` | 52 байта, NOLOAD; не лежит на рабочем стеке |
| Остальная TCM до `0x7000B000` | не выделена программе | не объявлена игровой кучей |

CPU работает с framebuffer через `0xF0002100`; DMA-резерв имеет CPU-алиас `0xF0000100`. **Реальный DMA не запускается:** применимость этих alias-адресов в регистрах DMA, в отличие от CPU-адресации, пока не подтверждена. Будущий bus/DMA address нельзя автоматически приравнивать к CPU uncached pointer.

Код и константы — XIP. Нет переносимого в PSRAM текста, RTOS, malloc-аллокатора или динамических выделений. На этом шаге heap — непрерывная зарезервированная область с linker-символами; подключение единого malloc относится к интеграции игры. В `.heap` применён NOLOAD, поэтому `size` включает весь резерв в BSS — это **не 4 МиБ занятых runtime-данных** и не большой flash BIN.

Требуемая проверка в linker script:

```ld
ASSERT((__heap_end - __heap_start) >= 0x200000,
       "Continuous heap smaller than 2 MiB")
```

Также проверены entry, размер vector template, framebuffer, выравнивание, конец heap и отсутствие пересечения с системным хвостом NOR. Для будущей игры ASSERT гарантирует **размер арены**, а не всегда свободный malloc-блок после выделений/фрагментации.

## 5. Порядок старта и тест памяти

1. ARM entry выставляет SVC, маскирует IRQ/FIQ. **Первая MMIO-запись** отключает WDT (`0xA0030000`, 16 бит, `0x2200`).
2. Выставляются UND/ABT/FIQ/IRQ/SYS/SVC SP. Номинальное stock-значение SVC — `0x70009C74`; перед первым вызовом C оно выравнивается до **`0x70009C70`**, поскольку исходное значение не кратно 8. Внутри C SP далее закономерно уменьшается на размер frames.
3. Создаётся TCM-mailbox; выполняются cache/remap-настройки: alias `[0xF0000000,0xF0400000)`, MPU/cache region 0 для полного NOR-окна `[0x10000000,0x10400000)`, резерв 32 КиБ кэша. Конец region0 намеренно расширен с начального stock `0x10001000` до `0x10400000`; это новое значение, а не извлечённая готовая последовательность. Полная новая композиция cache-control и handshake остаются аппаратными предпосылками, а не результатом теста телефона. EMI/PLL/PMIC voltage не перепрограммируются: используется состояние после BL2.
4. **До создания runtime-данных** выполняется разрушительный тест всех `0x400000` байт PSRAM из XIP с TCM-стеком: walking data bits, address-line sentinels, уникальные по адресу шаблоны, инверсии, нули/единицы с прямым/обратным проходом. Он обнаруживает зеркалирование и базовые дефекты, но не заменяет длительный стресс-тест при разных частотах/питании.
5. Только после успешного теста копируются 64 байта векторов в physical `0x0`, инициализируются `.data/.bss`, затем запускается экранная диагностика. Первые 256 байт остаются исключены из heap.

Это необходимое изменение порядка относительно буквального «сначала .data, затем полные 4 МиБ»: иначе тест стёр бы векторы, framebuffer и собственные глобальные данные. Исполнение теста из действующей stock MAUI/RTOS запрещено архитектурой: он уничтожает всю RAM и не возвращается в загрузчик. Нужен холодный handoff BL2 без фонового DMA в тестируемую память. При отсутствующей памяти, дающей bus abort вместо зеркала, корректный вывод ошибки на LCD не гарантирован.

Коды `psram_test`: 1 — data bus, 2 — address alias, 3/4 — адресный шаблон/инверсия, 5/6 — нули/единицы. На ошибке нет обращения к framebuffer в неисправной PSRAM: используется PIO красно-белая индикация, подробности — в TCM-mailbox. Ошибка cache/remap (`0xC1`) останавливает старт раньше LCD.

## 6. LCD и кнопки

### LCD

- Контроллер SoC `0xA0450000`; command/data `0xA0450F80/0xA0450F90`, 16-битные записи. ID читаются **8-битными** чтениями, как в stock-коде.
- GPIO45…49 переведены в mode 1 по stock mode-table file `0x83668`; затрагивается только LCD-подмножество, не вся modem/SIM/camera GPIO-конфигурация. Восстановлены gate bits 0/7, serial timing/config и связанное регистровое поле из stock LCD-пути.
- Стоковая таблица выбора по file `0x9D4D0` и связи с профилями восстановлены точнее, чем на шаге 1:

| Профиль | Ключ ID | Как составляется |
|---|---|---|
| B | `0x7C89` | `(DA << 8) | DB` |
| C | `0x9106` | `(DB << 8) | DC` |
| A | `0x3300` | `(DA << 8) | DB` |

Таблица подтверждает критерии stock-программы, **не физически установленный чип**. При совпадении профиль фиксируется; при неизвестном ID выполняется циклический показ **B → C → A**, по 32 итерации main loop. Время не объявляется секундами. Изменение keypad-mask с нажатой клавишей после первого кадра фиксирует выбранный fallback; при постоянном нулевом/нерабочем keypad он продолжит цикл.

Инициализационные команды хранятся в JSON с file offsets и генератором `.inc`. Пиксельные clear-loops stock-прошивки не ошибочно включены как параметры последней команды. Задержки реализованы консервативным busy-loop с настраиваемым `DELAY_LOOPS_PER_UNIT`; **это не калиброванные миллисекунды**. Унаследованные частоты, физические bus timings, подсветка, byte/BGR/orientation на конкретной панели ещё требуют проверки.

Вывод сейчас CPU/PIO: окно `2A/2B/2C`, два 8-битных переноса на RGB565-пиксель. Это преднамеренно простой тест, **не быстрый DMA-blit**, не видеоплеер и не обещание FPS. Время полной перерисовки ограничивает частоту опроса кнопок в этом диагностическом приложении.

### Keypad

- GPIO12…21 — mode 1 из той же stock mode-table, только нужные pinmux/pull-поля.
- KP `0xA00D0000`; читаются `0xA00D0004/08/0C/10`. На LCD видны четыре сырых 16-битных значения и `~raw` как 64-битная hex-маска.
- Для теста выбраны документированные scan/debounce settings: `KP_SCAN_TIMING=0x11`, `KP_DEBOUNCE=0x100` (8 мс по формуле datasheet), double-keypad mode. Это **выбранные диагностические**, не объявленные восстановленными stock-значения.
- Физическая привязка цифр/D-pad/softkeys не навязана. Не включены KP_MEM5, power key через PMIC и полноценная обработка ghosting. Отображаются именно биты 0…63, не гарантированно все клавиши телефона.

## 7. Результат параллельной дотрассировки

### MSDC0 / VMC

Подтверждены mode 1 для **GPIO31…36** и общий GPIO-init write loop. Найден **VMC_CON0 `0xA07001C0`**, rail-table и прямой RMW. Но установленная прямая операция добавляет только **bit11 (`0x0800`)** — это **не** доказанная установка EN/VOSEL и не доказательство напряжения 3,3 В. Сквозная цепочка SD power-on → VMC rail → enable/voltage → стабилизация **не восстановлена**. Поэтому SD/PMIC-записей «наугад» в диагностическом образе нет. Подробности и конкретные file offsets встроены в приложения.

### Audio

Поправка к запрошенной точке: **`0x1003066C` — не функция, а строка `hal\audio\src\v1\audio_service.c`**. Ближайшая обёртка `0x1003065C` согласуется с allocation/callback path, не с настройкой ЦАП.

Независимо от этой ошибки протрассированы `L1Audio_HISR` → `0x10013668`, setup/event-loop `0x10013728`, callback-таблицы и veneer в RAM. Подтверждены audio-related обращения `0x82207410`, `0x82207E56`, `0x82CA007C`, **но назначать им смысл DAC без доказательств нельзя**. Дальнейший путь требует восстановления упакованных RAM-областей. PCM/DAC/AFE power-on, rate и DMA пока не установлены; аудио в BIN не заявлено работающим.

## 8. Как воспроизвести сборку

Нужны Python 3 и распакованный Arm GNU Toolchain с `arm-none-eabi-*` в PATH. Makefile проверен GNU Make 4.4.1. Исходный dump читается только для board-template, по умолчанию из переданного пользователем пути.

```powershell
# Выполнять из распакованного каталога проекта.
make check
# При другом пути к dump:
make check "DUMP=C:/path/to/kenshi_mini2_full.bin"
# Если GNU Make не установлен, эквивалентная проверенная сборка:
python tools/build.py --prefix arm-none-eabi- --dump C:/MTK_Drivers/dump_tool/kenshi_mini2_full.bin
# Отрицательный тест ASSERT:
make check-heap
```

Если compiler-prefix содержит путь с пробелами, Python builder передаёт его отдельным argv; Makefile также заключает compiler/objcopy/size в кавычки. `DUMP` рекомендуется передавать без пробелов, так как это также dependency GNU Make.

Для дополнительных, **не обязательных для компиляции**, ARM-эмуляционных проверок установите закреплённые `requirements-test.txt` в отдельное Python-окружение и выполните:

```powershell
make check-emu
# либо:
python tests/emulate_psram.py
python tests/emulate_startup.py
```

Локальная проверка этого чата использовала изолированные host-зависимости в рабочем каталоге, без установки пакетов в проект пользователя. В архиве нет compiler binaries, Python wheels, полного NOR и уникальных пользовательских данных системного хвоста.

## 9. Ограничения до аппаратного допуска

1. Подтвердить flash erase geometry и восстановление до записи, а не полагаться на логическое смещение `0xB000`.
2. Проверить принятие GFH/opaque MAUI metadata и новый handoff BL2. GFH FILE_INFO имеет заданные значения, но одной компиляции недостаточно.
3. Подтвердить фактические EMI, PSRAM 4 МиБ, cache/MPU/remap-композицию и ёмкость/доступность TCM выбранной ревизии; код не угадывает EMI timings.
4. Проверить LCD ID, тайминги/подсветку/ориентацию, стабильность PIO-цветов, физическую keypad-mask.
5. Проверить адресацию/когерентность реального DMA отдельно; текущий CPU-алиас не является доказательством доступности alias с периферийной шины.
6. Закрыть VMC power/voltage и реальный AFE/DAC path до SD/аудио HAL. Не отключать вслепую общие DSP/clock domains.

**Итог:** требования к структуре проекта, entry, C99-сборке, GFH-упаковке и 2-МиБ link-time heap реализованы и проверены офлайн. Готов диагностический кандидат для отдельного контролируемого bring-up, но аппаратный тест телефона ещё не выполнен. Шаг 3 — порт игры и полноценный медиа-HAL — не начат. Исходный dump и отслеживаемые файлы `dump_tool` не изменены.

##### 3.1. I/O-контроллер: подтверждённые маски, неизвестное начальное значение

Функция file `0xF7A0` / CPU `0x1000F7A0` (`E07`) использует base `0xA0130000`, literal file `0xF7E0`. Её записи:

- file `0xF7B4`, CPU `0x1000F7B4`, `STR` в **MSDC_IOCON `0xA0130014`**: сохраняет bits31:8 старого значения, bits7:0 заменяет младшим байтом результата `BL 0x10251B78` (call file `0xF7AA`, bytes `42 f2 e5 f9`).
- file `0xF7BE`, CPU `0x1000F7BE`: `MSDC_IOCON |= 0x00280000` (`5 << 19`).
- file `0xF7CE`, CPU `0x1000F7CE`: `MSDC_IOCON = (MSDC_IOCON & ~0x03000000) | 0x01000000`.
- file `0xF7DC`, CPU `0x1000F7DC`: **MSDC_IOCON1 `0xA0130018` = `0x00022222`** (literal file `0xF7E8`).

**Не восстановлен результат `0x10251B78`.** Нельзя подставлять вымышленный low byte IOCON или утверждать точную начальную drive/slew-конфигурацию. Номинальные байты raw file `0x251B78` не приняты за код этой runtime-функции: отображение упакованного компонента не восстановлено (`E21`).

Важно: маска `0x00280000` применяется к **IOCON** `0xA0130014`, а не к **CFG** `0xA0130000`. Совпадение номера bit21 не делает эту запись управлением VDDPD/VMC. В datasheet у MSDC_CFG bit21 есть название VDDPD; это не подтверждает управление VMC через данную IOCON-запись или через разводку платы.

##### 3.2. Reset/часть подготовки — не PMIC

`0x100373E4` (`E08c`) выполняет 32-битный RMW `MSDC_CFG |= 2`, проверяет bit1 и, при превышении разницы счётчика `2`, выполняет `MSDC_CFG &= ~2`. Единицы времени счётчика здесь не установлены; это **не задержка стабилизации VMC**.

`0x100117A0` (`E08a`):

- file `0x117AA`: `MMIO32[0xA0130080] &= ~0x80`;
- file `0x117B6`: через `0x10037754` задаёт field mask `0xFF000000` регистра `0xA0130020` значением `0x50` (результат `(old & ~0xFF000000) | 0x50000000`);
- file `0x117C2`: `MMIO32[0xA001010C] |= 1`;
- file `0x117CE`: `MMIO32[0xA0130000] &= ~0x18`;
- file `0x117DA`: вызывает `0x10013E9C` с `r0=0xF0`, то есть дальнейшую настройку SD clock divider. Не приписываю этому значение напряжения питания.

Общий field-writer `0x10037754` прочитан (`E08d`): `(old & ~mask) | (value << ctz(mask))`; дополнительного ограничения shifted value маской в нём нет. Приведённые выше конкретные аргументы помещаются в соответствующие поля.

`0x1003BE00`, вызываемый из SD init, формирует сервисный запрос: byte0=`0x12`, word по `+4`=`1`, команда `r1=2`; сам wrapper не пишет `VMC_CON0` (`E12a`). Само наличие `0x12` **не связывает** запрос с rail-id `0x12` из другой таблицы: пространства идентификаторов и конечный обработчик должны быть доказаны отдельно.

#### 4. VMC/PMIC: что действительно найдено в дампе

##### 4.1. Четыре буквальных вхождения `0xA07001C0`

Поиск little-endian слова по всему дампу с шагом 2 (`E18`) дал:

| File слова | CPU-адрес слова | Роль |
|---|---|---|
| `0x00004270` | `0x10004270` | Literal прямого RMW в BL2-функции `0x1000414C` |
| `0x00008560` | `0x10008560` | Поле base в BL2 rail-записи, начало записи file `0x855C` |
| `0x00010BF4` | `0x10010BF4` | Literal прямого RMW в main-функции `0x10010AD0` |
| `0x0006D350` | `0x1006D350` | Поле base в main rail-записи, начало записи file `0x6D34C` |

Обе rail-записи имеют слова `{0x00000012, 0xA07001C0, 0x00000000}`. Это **данные, не инструкции записи питания**.

Значение `0xA07001C4` как выровненный на 2 байта literal не найдено. Это не доказательство отсутствия обращений к VMC_CON1: адрес может получаться как `base+4`.

##### 4.2. Прямые операции: только установка bit11

| File кода | CPU кода | Операция |
|---|---|---|
| `0x416C…0x4174` | `0x1000416C…0x10004174` | Загрузить literal `0xA07001C0`, `LDRH`, `BIC #0x0800`, `ORR #0x0800`, `STRH` |
| `0x10AF0…0x10AF8` | `0x10010AF0…0x10010AF8` | Та же последовательность |

`r3=0x0800` получен из `1 << 11`, `r2=r3` (`E09b/c`). Эквивалент обеих последовательностей:

`MMIO16[0xA07001C0] = (old & ~0x0800) | 0x0800`.

Результат — установка bit11 с сохранением остальных прочитанных битов. В локальном описании VMC_CON0 этот bit не назван среди EN/ON_SEL/VOSEL, и смысл ему не присваивается.

BL2 caller подтверждён: file `0x330C` / CPU `0x1000330C` вызывает `0x1000414C` **при нулевом результате** предыдущего вызова `0x10005C74` (`E09a`). Связь этой общей PMIC-настройки с SD и фактическое выполнение данной ветви при конкретной загрузке не доказаны. Для `0x10010AD0` прямой caller в выполненном Thumb-скане несжатой части не найден; это не означает «никогда не вызывается».

Следующая инструкция загрузки VMC base (file `0x4176` / `0x10AFA`) затем делает `base += 0x60` и обращается по `+0x1C`: фактический адрес **`0xA070023C`**, уже **не VMC_CON0/1**. Нельзя присоединять последующие PMIC writes к VMC только из-за повторной загрузки этого literal.

По локальному datasheet (`E20`):

- VMC_CON0 bit0 — `RG_VMC_EN`;
- bit1 — `VMC_ON_SEL` (software EN при 1; аппаратный путь при 0);
- bits6:4 — `RG_VMC_VOSEL`;
- bit10 — `RG_VMC_NDIS_EN`;
- bit15 — status.

Найденный `0x0800` не совпадает ни с EN, ни с ON_SEL, ни с полем выбора напряжения. Reset defaults datasheet не используются как значения, выбранные прошивкой Kenshi Mini 2.

##### 4.3. Восстановлен общий механизм PMIC setter, но не SD-выбор rail

Функция file `0x13060` / CPU `0x10013060` (`E10a`):

1. Читает `index = MMIO/RAM8[0xF00A835E + r0]` — **RAM**, не ROM.
2. Выбирает `base = ROM32[0x1006D2E0 + index*12 + 4]`.
3. Вызывает `0x1003635C`, сохраняя входные `r1=field_index`, `r2=value`.

У rail-таблицы stride=12; VMC — запись **index 9**, file `0x6D34C`, CPU `0x1006D34C` (`E16`). Наличие в первом слове записи числа `0x12` само по себе не доказывает `RAM8[0xF00A835E+logical_id] == 9` для SD-запроса.

Общий setter file `0x3635C` / CPU `0x1003635C` (`E10b`):

- field-table base `0x1006D37C`, stride=6;
- byte `+1` = byte-offset регистра относительно rail base;
- halfword `+2` = mask;
- byte `+4` = shift;
- чтение `LDRH` file `0x36370`, запись **`STRH` file `0x3637E`**, CPU `0x1003637E`;
- значение: `(old & ~mask) | ((value << shift) & mask)`.

Вокруг RMW есть вызовы `0x1000C068` / `0x1000C060`; сам факт вызовов подтверждён, отдельное поведение этих служебных функций здесь не переопределяется.

| Индекс поля | File / CPU записи таблицы | Offset | Mask | Shift | Что следует из данных |
|---|---|---|---|---|---|
| `0` | `0x6D37C` / `0x1006D37C` | `0` | `0x0001` | `0` | При выборе VMC меняет его bit0 |
| `1` | `0x6D382` / `0x1006D382` | `0` | `0x0002` | `1` | При выборе VMC меняет bit1 |
| `3` | `0x6D38E` / `0x1006D38E` | `0` | `0x01F0` | `4` | Общее 5-битное поле; не объявляется безусловно VMC VOSEL |
| `5` | `0x6D39A` / `0x1006D39A` | `0` | `0x0800` | `11` | Общее поле bit11 |
| `0x12` | `0x6D3E8` / `0x1006D3E8` | `0` | `0x0070` | `4` | Маска совпадает с VMC VOSEL, но SD caller с этим полем не установлен |

**Два разных `0x12`:** rail-id в 12-байтной таблице и индекс поля в 6-байтной таблице — разные сущности. Их нельзя отождествлять.

Диспетчер file `0x106E8` / CPU `0x100106E8` читает logical rail из byte0 входной структуры (`E11a`). Проверены ветви:

- команда `2`: `r2 = word[input+4]`, field `0`, общий переход к call file `0x107A2`;
- команда `0x1FB`: `r2 = byte[input+1]`, field `1`, тот же общий call;
- команда `0x1FA`: `r2 = byte[input+1]`, field `2`, тот же call;
- команда `4`: сначала lookup через `0x100354F8`, затем field `3` и call file `0x1073A`; следом `0x10033730` (`E11b/c`).

Для выполнения VMC enable посредством этого маршрута нужны как минимум доказанные logical rail, runtime-mapping к index9, команда/field и value. Их SD-специфическое сочетание **не установлено**, поэтому таблица setter не превращается в утверждение о включении VMC.

`0xF00A835E` попадает в startup zero-область `0xF00541E4…0xF014CA70`: операция zero вызывается file `0x5D67C` / CPU `0x1005D67C` с размером `0xF888C` (`E13`, также проверен существующий scatter). Нельзя принять первоначальные нули BSS за рабочую инициализированную PMIC mapping-таблицу. Заполняющий её этап в этой подзадаче не восстановлен.

##### 4.4. Что не следует путать с VMC

- `0xA0700A00`, объявленный `PMIC_ADDR` в локальном `fernly-fernvale-pmic.h`, **не** равен `VMC_CON0 = 0xA07001C0`.
- Wrapper file `0x37420` / CPU `0x10037420` действительно вызывает общий PMIC-setter с base **`0xA0700A00`**, file call `0x37428` (`E12b`). Это не основание назвать его VMC enable.
- MSDC reset, GPIO mode, controller clock divider, IOCON и service request с byte `0x12` не заменяют доказанного PMIC EN/VOSEL-пути.

#### 5. Что подтверждено и что остаётся открытым

| Вопрос | Статус |
|---|---|
| MSDC0 base `0xA0130000` | **Подтверждено** literal и MMIO инструкциями |
| SD alternate mode GPIO31…36 | **Подтверждено** ROM-таблицей и общим write-loop |
| GPIO_MODE3/4 значения | **Подтверждено:** `0x11111101` / `0x11111111` |
| Специальные SD pull R0/R1 на общем init-этапе | **Подтверждено:** relevant R0=R1=0; последующие изменения/внешние резисторы неизвестны |
| Полный начальный low byte MSDC_IOCON | **Не подтверждено:** результат `0x10251B78` не восстановлен |
| MSDC_IOCON1 write | **Подтверждено:** `0x00022222` |

| Наличие/подключение VDDPD к VMC на плате | **Не установлено** |
| Фактический card-detect GPIO/полярность, режим питания отсутствующей карты | **Не установлены**; SD callback boundary по slot `+0x60` отмечен в `E14`, но функция не названа по догадке |

##### Ограничение отрицательных результатов

Поиск буквальных слов выполнен по всему дампу, прямых Thumb-call candidates — по несжатой области до file `0xA2CB0`. Проверены перечисленные тела функций и ветви; сплошной дизассемблированный поток, literal pool или совпадение байтов не принимались сами по себе за исполняемый код. Не восстановлены все косвенные callbacks, runtime-инициализация RAM mapping и упакованный компонент. Поэтому «цепочка не доказана» не означает «в прошивке нет такой цепочки».

**Практический итог анализа:** pinmux можно документировать как подтверждённый статический факт штатной общей инициализации. Для VMC пока допустимы только адрес регистра, буквальный RMW bit11 и общий механизм PMIC setter. Рабочие EN/VOSEL, напряжение и задержки для будущего SD-драйвера из этих данных назначать нельзя.

## Приложение В. Подробная дотрассировка аудио

### Kenshi Mini 2 — шаг 2: дотрассировка аудио AFE/ЦАП

**Дата:** 16 ноября 2026 года. **Режим:** только статическое чтение, без исполнения firmware и без доступа к устройству.

#### 1. Главный результат и поправка к исходной точке

**`CPU 0x1003066C / file 0x3066C` — не функция, а начало ASCII-строки `hal\audio\src\v1\audio_service.c`.** Строка вместе с NUL занимает `[file 0x3066C, 0x3068D)`. Её Thumb-дизассемблирование даёт формально допустимые, но ложные инструкции. Делать из них MMIO-трассу нельзя.

Перед строкой действительно находится маленькая функция по `CPU 0x1003065C / file 0x3065C`: она передаёт эту строку и номер исходной строки в обёртку над callback. По дальнейшему коду это **allocator-like API, а не настройка ЦАП**. Второй экземпляр строки у `file 0x5C250` также привязан к software callback, не к установленной DAC-последовательности.

Независимо от ошибочной исходной точки удалось углубить **настоящую аудиоветвь**: дескриптор `L1Audio_HISR` → `0x10013668`, setup/event-loop `L1Audio` у `0x10013728`, программные таблицы callbacks, DSP/DPRAM-обращения и ARM-veneer в RAM-код `0xF024…`, `0xF02F…`, `0xF031…`. **Это отдельная подтверждённая зацепка, а не найденный вызов из строки `0x1003066C`.**

**Итог по ЦАП:** в протрассированных участках **нет операций, которые можно уверенно назвать включением DAC, подачей PCM, выбором sample rate или настройкой аналогового выхода**. Есть точные audio-related обращения к DPRAM/MMIO; их нельзя повышать до статуса DAC. Сквозной путь PCM → DSP/AFE → аналоговый выход пока не восстановлен.

#### 2. Объект, адреса и свидетельства

- Исходный дамп: `C:\MTK_Drivers\dump_tool\kenshi_mini2_full.bin`.
- Размер: `0x400000` = 4 194 304 байта.
- SHA-256 до и после чтения: `9109aa340956f2da8cd981b4501c1803d14f097b331709cc7187c6ff2005fafc`.
- Машиночитаемое дизассемблирование/байты/поиски: `встроенное приложение с audio-дизассемблированием ниже` — разделы **E01–E27**.
- Для обычного исследованного NOR/XIP-кода: `CPU = file + 0x10000000`. Для действительно скопированного RAM-кода ниже отдельно показано преобразование.
- Все интервалы справа открыты. Адрес Thumb-указателя с младшим битом 1 отделён от адреса первой инструкции.

Уверенность:

- **D** — байты, вычисленный literal/ADR, конкретная инструкция, статическая связь вызовов/таблиц.
- **I** — согласованная интерпретация software-механизма; это не измерение на плате.
- **R** — сведения из локального reference-кода, не подтверждение использования в данном firmware.
- **?** — отсутствуют байты соответствующей исполняемой области либо не установлена семантика регистра/формата.

Имена функций ниже аналитические; символы из исходников не восстановлены. Дизассемблирование не доказывает, что ветвь реально выполнялась на конкретном устройстве.

#### 3. Что реально находится около `0x1003066C`

##### 3.1. Ближайшая функция `0x1003065C` — allocator-like, не AFE [E01–E03]

| CPU / file | Наблюдение | Статус |
|---|---|---|
| `0x1003065C / 0x3065C` | `PUSH {r4,lr}` | D |
| `0x1003065E / 0x3065E` | `LDR r2,[PC,#8]`, pool `file 0x30668` = `0x000006A4` (1700) | D |
| `0x10030660 / 0x30660` | `ADR r1,…` → ровно `0x1003066C` | D |
| `0x10030662 / 0x30662` | `BL 0x10038DA8` | D |
| `0x10030666 / 0x30666` | возврат; дальше literal, затем строка | D |

`0x10038DA8` сохраняет входной `r0` как размер, при нуле возвращается; иначе загружает таблицу `T = 0xF005922C` (literal `file 0x38DC8`), вызывает `BLX [T+4]`, а при ненулевом результате обнуляет полученный блок длиной, равной исходному `r0`, через `0x100429F0`. ARM-код `0x100429F0` явно пишет нулевые байты/halfwords/words в переданный адрес.

**D:** вызов provider в ячейке `0xF0059230` и обнуление результата. **I, высокая:** zero-initializing allocation с file/line tracking. Строка `audio_service.c` говорит о вызывающем исходном модуле, а не превращает allocator в аудиорегистр. Значение `0x6A4` — передаваемый номер строки, не коэффициент DAC.

**Неразрешённый хвост:** фактический указатель `[0xF0059230]` в этом исследовании не восстановлен. Назначать этому callback имя DAC-функции нельзя. В просканированных кандидатах прямых ARM/Thumb-вызовов исходной обёртки в основном коде входящего ребра не найдено; абсолютного raw-указателя `0x1003065C`/`0x1003065D` во всём образе тоже нет. Это не исключает вызов из распакованного кода или вычисляемый адрес.

##### 3.2. Вторая строка и другая обёртка [E04–E06]

- Функция `CPU 0x1005C23C / file 0x5C23C` кладёт `r0` на стек, задаёт `r2 = 0x6A9` (1705, pool `file 0x5C24C`), `r1 = 0x1005C250`, `r0 = sp`; вызывает `0x1003E000`.
- `0x1003E000` загружает **другой** callback `[0xF005922C+8] = [0xF0059234]` и делает `BX`. Его реализация/точная семантика неизвестны. Интерфейс с адресом локального слота согласуется с освобождением/управлением памятью, но **это только гипотеза**, не восстановленное имя `free`.
- Существует абсолютный Thumb-указатель `0x1005C23D` в pool `file 0x294AC`. `CPU 0x10029470` загружает его в `r1`; `0x10029474` кодирует `BL 0x1036EDF8` с `r0 = 1`. По `file 0x36EDF8` в текущем NOR стоят `FF`. Поэтому не объявляю это доказанной runtime-регистрацией или реально доступной функцией: исполняемое отображение этой цели не установлено.

Ни в одной из этих коротких обёрток нет установленного доступа к AFE/DAC.

#### 4. Настоящая аудиоветвь: `L1Audio` и HISR

##### 4.1. Надёжные входные зацепки [E07–E10]

**Дескриптор HISR**, `file [0x61F40,0x61F50)`:

| file | Значение | Что доказано |
|---|---|---|
| `0x61F40` | `0x00010108` | первый байт — логический ID `8`; остальные поля здесь не названы аппаратными IRQ |
| `0x61F44` | `0x00000300` | raw-поле; это не доказанный размер PCM/DMA-буфера |
| `0x61F48` | `0x10013669` | Thumb-entry `CPU 0x10013668` |
| `0x61F4C` | `0x1009A348` | строка `L1Audio_HISR` в `file [0x9A348,0x9A355)` |

Связь не ограничена похожей строкой: `0x10013734` задаёт ID `8`, `0x10013736` вызывает `0x10037BC8`; та процедура действительно ищет запись по первому байту в таблице `0x10061F20`, с шагом `0x10`, и передаёт указатель entry/name дальше в `0x10012E78`. Поэтому связь `L1Audio setup → HISR ID 8 → 0x10013668` подтверждена статически. **ID 8 — индекс software-дескриптора, не восстановленный номер аппаратного аудио-IRQ.**

У `CPU 0x10013728 / file 0x13728` есть setup и бесконечный event-loop. `0x1001372A` делает `ADR r0` на строку `L1Audio` по `0x10013844`. Через pool `file 0x1384C` используется общий контекст **`C = 0xF005925C`**. Именование процедуры `L1Audio setup/event-loop` — I по строке и структуре; её непосредственный caller/запись планировщика здесь не восстановлены.

##### 4.2. Программные callback-таблицы, не PCM FIFO [E10, E13–E17]

Удалось согласовать записи и чтения одного контекста:

| Поле относительно C | Адрес/размер группы | Установленное использование |
|---|---|---|
| `C+0x1C` | `0xF0059278` | handle, возвращённый созданием/получением HISR по ID 8 |
| `C+0x20+4*i`, `i<18` | `0xF005927C…` | callbacks task-loop; setter `0x1005A110`, косвенный вызов `0x1001382E` |
| `C+0x68+4*i`, `i<18` | `0xF00592C4…` | аргументы task-loop; setter/poster `0x10034484` |
| `C+0xB8+4*i`, `i<5` | `0xF0059314…` | callbacks HISR; запись в `0x1005B8CC`, вызов `0x100136A8` |
| `C+0xCC+2*i`, `i<5` | `0xF0059328…` | 16-битные ID пяти HISR slots |
| `C+0xD8+4*i`, `i<5` | `0xF0059334…` | аргументы для пяти HISR callbacks |
| `C+0xEC` | `0xF0059348`, 16 бит | pending mask пяти HISR slots |
| `C+0xB4` | `0xF0059310`, 32 бита | pending mask для 18 task events |

`0x1005B8CC` ищет свободный ID среди пяти слотов, записывает ID/callback/argument. `0x1001C3E4` ищет совпадающий ID, ставит бит в `C+0xEC` и вызывает software-механизм активации по handle `C+0x1C`. HISR `0x10013668` очищает биты и вызывает зарегистрированные функции; затем передаёт 18-slot события в task через `0x10034484`. В task-loop `0x10013828–0x1001382E` загружаются аргумент и callback, после чего выполняется `BLX r1`.

**D:** это реальные таблицы указателей и событий. **Не установлено:** какие callbacks отвечают именно за PCM downlink, их фактические RAM-значения на работающем устройстве, адрес/формат аудиобуфера. Числа 5 и 18 — количества software slots, а не DMA channels, sample width или размеры блоков.

##### 4.3. DSP-command bridge [E15]

`CPU 0x1001B84C / file 0x1B84C` сохраняет входное 16-битное значение в `C+0x0E`, сохраняет timestamp в `C+0x10`, выполняет одну MMIO-запись (ниже), вызывает RAM-процедуры через veneer и далее:

- `0x1001B8A2` / `0x1001B8CE` → `0x1001C3E4` для dispatch по ID;
- в fallback сохраняет значение в `C+0x0C`, затем вызывает `0x1003B6F4` с HISR handle.

**I:** мост DSP/аудиособытия в `L1Audio_HISR`. Конкретный hardware-IRQ, точный формат команд и смысл отдельных значений не установлены. Это ещё не поток PCM и не запись в DAC.

#### 5. Вызовы и literal pools, где трасса уходит в RAM

- `file 0x9B7D8` → `CPU 0x000012C8`: `PUSH; BLX 0x00000BA4; POP`;
- `file 0x9B0B4` → `CPU 0x00000BA4`: ARM-veneer на Thumb `0x100426AC`;

#### 6. Подтверждённые MMIO/DPRAM-последовательности — и что они НЕ доказывают

| CPU instruction / file | Операция | Literal pool | Классификация |
|---|---|---|---|
| `0x10021E7C / 0x21E7C` | `STRH 0xFFFF → 0x82207410` | `file 0x21E8C` = `0x82207400` | D: запись в обёртке входа HISR. R: окно DPRAM по reference. Назначение битов/полярность mask неизвестны |
| `0x1001367C / 0x1367C` | `LDRH ← 0x82207E56` | `file 0x13724` = `0x82207E40` | D: чтение перед callback-dispatch при ненулевом pending mask. Возможны status/synchronization; это гипотеза, не DAC FIFO |
| `0x1001B872 / 0x1B872` | `STRH 1 → 0x82CA007C` | `file 0x1B8F0` = `0x82CA0060` | D: запись в DSP-command bridge. ACK/handshake возможен, но точное имя регистра/бита не установлено |
| `0x100426B6 / 0x426B6` | `LDR 32-bit ← 0xA0180088` | `file 0x426F4` = `0xA0180080` | D: timestamp-ветвь; не доказанный DAC/sample counter |

Последовательность в HISR: software-обёртка с записью `0xFFFF` → проверка pending mask → чтение `0x82207E56` → очистка software-бита и косвенный callback → дальнейший dispatch → выходная обёртка с RAM-хвостом. Точные значения callbacks не восстановлены; без них нельзя дорисовать «подачу следующего PCM-блока».

**Подтверждённых DAC-операций в этой трассе: 0.** Подтверждённый DSP/DPRAM доступ не равен DAC, audio DMA или analog power-up. Нет доказанного `DAC enable`, `PCM FIFO write`, `sample-rate set`, `mute/unmute`, `speaker/headphone routing`, DAC gain или запуска audio DMA.

Результаты поиска в исходном NOR:

1. В primary-области `file [0,0xA28B0)` **нет 4-byte-aligned слов** ни из `0x82CD0000…0x82CDFFFF`, ни из `0xA0720000…0xA072FFFF`.
2. Кандидатный поиск Thumb16 `LDR [PC,imm]` в `file [0xB5B0,0x5D50C)` также не дал literal-доступов к этим окнам. Это поиск конкретной формы адресации, не полная символьная эмуляция.
3. Во всём образе есть 8 aligned-слов из первого полного 64-KiB окна и 13 из второго, но **все вне primary-области**, в упакованных/неподтверждённых данных. Это не MMIO-xrefs. Сканирование всех byte alignments нижних 4 KiB даёт отдельные случайные совпадения; список сохранён в E26.
4. Особенно нагляден ложный ABB-кандидат у `file 0x5F203`: четыре байта дают `0xA07206E1`, но они пересекают границу ARM-инструкций `LDRH`/`LSL`, а не являются literal pool.

**Отсутствие этих literals не доказывает отсутствия AFE в firmware.** База может вычисляться, передаваться через RAM или находиться внутри распаковываемого кода. Здесь отрицательный результат только не позволяет подтвердить reference-адреса по наблюдённым MMIO.

Есть и **конфликт карт из references**: старые `AFE_VAG_CON/AFE_VAC_CON…` в `afe.h` используют `MIXED_BASE+0x100`, тогда как Fernly называет `0xA0170100` `MPLL_CON0`. Boot-код по `0x10009166`/`0x10009184` действительно читает `0xA0170100`, выделяет шестибитное поле и сравнивает с `0x18`/`0x14`; затем настраивает `0xA001011C`/`0xA0010108`. Превращать это чтение в DAC gain на основании одного совпавшего адреса нельзя; аудио-reachability для него нет.

`afe.c` пригоден для гипотез о типах блоков, но не как восстановленная последовательность Kenshi. Например, `BeepHz` прямо содержит эмпирическое предположение о внутреннем делителе `N=32`. Ни эта частотная формула, ни функции `AFE_initialize`/`AFE_EnsureOutputPath` не являются доказательством из дампа. Их код не переносился и не запускался.

#### 8. Что осталось неизвестным и точное продолжение read-only анализа

1. **RAM-код AFE:** восстановить проверяемое отображение/распаковку прежде всего для entries `0xF0247B08`, `0xF0247C00`, `0xF0247CFC`, `0xF02F8B5A`, `0xF02F95D4`, затем выходного хвоста `0xF03116B4`. Отслеживать literal pools и вычисление баз уже в достоверных RAM-байтах. Без этого имя «AFE-init» остаётся гипотезой.
2. **Callbacks:** установить реальные записи в `C+0xB8`, `C+0x20`, provider `T+4/T+8`; связать конкретные функции с PCM downlink, а не с общим DSP/GSM/audio dispatch. Текущие таблицы содержат адреса функций/аргументы, а не найденные PCM samples.
3. **Данные/тайминг:** неизвестны PCM/DSP buffer addresses, ring layout, sample width, mono/stereo, поддерживаемые частоты, реальный счётчик потребления samples, DMA descriptors и hardware IRQ. ID HISR `8` и поле `0x300` их не заменяют.
4. **Аналоговая часть:** не установлены clock/power/reset, DAC gain/mute, de-pop, выбор динамик/наушники, внешний amplifier-enable и соответствие ревизии SoC/платы.
5. **Память/отключение GSM:** из найденного DSP-пути нельзя заключать, что допустимо выключить общие DSP/clock domains; доступ audio DMA к SRAM/TCM не доказан.

Никакого аудиодрайвера, тестового тона или записей MMIO не создавалось и не выполнялось. Исходный дамп, helper, references, существующие отчёты, repo/проект не редактировались; новые материалы этой подзадачи — только этот файл и приложение E01–E27.
