## 2. Что действительно делает загрузчик

ARM_EXT_BL имеет диапазон файла `[0x2800,0xA248)`; его GFH declares длину `0x7A48`. Участок `[0xA248,0xB000)` полностью заполнен FF. **На границе 0xAFFF нет исполняемого кода, падающего в MAUI.** Реальная передача управления расположена значительно раньше:

* `0x10003D08` возвращает базу GFH MAUI `0x1000B000`.
* `0x10003456` ищет тип файла `0x0100`; `0x100033E0` / `0x10003A00` проверяют FILE_INFO: magic, имя, допустимую длину, content offset, max/file size, согласованность signature type/length и границы jump offset.
* `0x100031C4` находит MAUI_INFO (GFH type `0x0200`). `0x10002C7C` проверяет paired version; `0x10002DA4` получает feature word из MAUI_INFO, `0x10002C24` / `0x10002FFC` проверяют совместимость с BL2.
* `0x10009024` вызывает штатный accessor `0x10003114`, читает `[GFH+0x30]` и складывает с базой GFH. Получается **`0x1000B5B0`**.
* `0x10009078`: `movs r0,r4`; `0x1000907A`: `blx 0x10009F3C`; `0x10009F3C`: **`bx r0`**. Поскольку entry чётный, переход в **ARM state**, не Thumb.
* Заводской MAUI начинает с `LDR pc,[pc,#0x18]` и вектора на **`0x1000B670`**. Старый Тетрис начинает непосредственно с ARM `MRS r0,CPSR`. Оба варианта допустимы для показанного BX; обязательность заводской таблицы векторов в начале payload не обнаружена.

### Регистры и состояние

На последнем BX гарантируется `r0=r4=0x1000B5B0`, LR от BLX равен `0x1000907F`. `r3` в этой ветви указывает на локальную ячейку флага по текущему SP загрузчика. **SP не устанавливается загрузчиком в 0x70009C74 при handoff** — это стек, который заводской MAUI настраивает сам позднее. Остальные регистры, режим CPU и IRQ/FIQ, кроме изменения T при BX, наследуются и не являются публичным контрактом для нашего reset-кода.

В Unicorn для явно заданной фикстуры SVC/CPSR `0xD3`, входного SP `0x7000A600` получены SP `0x7000A5F0`, CPSR `0xD3`, LR `0x1000907F`. **Это не измерение регистров телефона и не универсальные значения.** Новый Reset_Handler сам маскирует IRQ/FIQ и выставляет банковые стеки.

### Заголовок не оказался доказанной причиной

Для старого и нового Тетриса родные инструкции валидатора возвращают 0, MAUI_INFO/paired version/features принимаются, точка входа разрешается правильно. От эталонного GFH у старого образа отличаются только два слова: `file_length: 0x978B0 -> 0x3380`, `max_file_size: 0xFFFFFFFF -> 0x37E000`. Ни одно из этих изменений не отвергнуто исследованными проверками.

У MAUI `signature_type=0`, `signature_length=0`. В перечисленных проверках GFH/handoff нет расчёта CRC/SHA по новому payload. Это **не утверждение об эмуляции всех ветвей BootROM/BL1/BL2 или полной холодной загрузки**. Подписанные загрузчики и проверки безопасности не патчились и не обходились.

У нового образа тот же корректный адрес/offset: load `0x1000B000`, content/jump `0x5B0`, entry `0x1000B5B0`. Длина файла `0x3418`; max_file_size теперь ограничен четырьмя секторами: `0x4000`.

## 3. Подсветка и первый кадр

В исходном Тетрисе **вообще нет записи, включающей ISINK**. Его Unicorn-прогон выполняет Sleep Out/Display On и отправляет кадр, но оставляет `0xA0700C10/0xA0700C20 = 0`. LCD `0x29` не включает внешний токовый драйвер подсветки. Поэтому отсутствие изображения при тёмной подсветке нельзя автоматически объяснять GFH.

Просканирован весь эталон: прямые PMU/PWM literals, Thumb callsites и исходные таблицы. В несжатой части восстановлена цепочка:

* ROM-таблица дескрипторов file `0x6D538`: индексы 0/1/2 -> `0xA0700C00/0xA0700C10/0xA0700C20`.
* ROM-таблица полей file `0x6D37C`: field `0x10/0x11` — bit0; field `0x12` — mask `0x0070`, shift4.
* `0x10013034` выбирает базу; `0x1003635C` выполняет настоящий 16-bit RMW. Эти инструкции прогнаны в Unicorn без замены самого setter.
* `0x10010CB8` / `0x10010CF4..0x10010D1A` задают исходный режим и уровень 24 для двух каналов. `0x10021A48` / `0x10021A7E,0x10021A8E` включают/выключают оба канала через команду `0x1B58`.
* Верхний caller `0x10033844..0x10033900` также управляет brightness/PWM-провайдером. Его callback-таблица находится в исходной `.data` (RAM `0xF0052CA0`, ROM source file `0x9F784`); часть целевых virtual addresses уходит в упакованную MAUI_BODY. Их нельзя дизассемблировать как код по одноимённому сырому file offset. Полный PWM runtime и разводка платы не восстановлены; они **не выдаются за проверенные**.

Названия регистров сверены с исходным MT6261 PMU driver проекта MediatekInfo/DZ09 (фиксированный commit `1b73af6d7876db5c468c5738de5b7536c7288108`, `Source/Lib/MT6261/Drivers/pmu.h`, строки 577–603); это внешний первичный исходник, не схема Kenshi. Собственный драйвер не копирует реализацию оттуда.

Новый bring-up использует **постоянный ток, не непроверенный PWM callback**: отключить оба канала; mode bit0 в `0xA0700C00` установить; на обоих каналах выбрать минимальный документированный шаг 4 мА, выключить DOUBLE, включить BIAS и затем EN. При нулевой исходной фикстуре получается mode=1, оба channel control=9. Маски сохраняют остальные биты; проверено на пяти разных начальных значениях регистров. Никаких случайных GPIO, KPLED или изменений напряжений питания.

Перед тестом всей PSRAM код инициализирует LCD, выбирает B/C/A по ID (при неизвестном ID — B) и PIO отправляет **ровно 40 960 байт RGB565**: красно-зелёно-синие полосы и белая T-фигура. Этот путь не требует framebuffer/PSRAM. Позднее выводится штатный кадр привязки кнопок, затем остаётся прежний игровой цикл Тетриса. Все три ID-профиля и неизвестный ID проверены. Физическую видимость fallback B на неизвестной панели модель не доказывает.

Дополнительно на bring-up оставлены выключенными MCEN/MPEN/MPDEFEN: старый код сам включал новую, аппаратно не подтверждённую MPU/cache-композицию до первого кадра. Алиас `0xF0000000` сохраняется, критические стеки — в TCM. Это диагностический выбор для изоляции проблем, а не оптимизация скорости. PLL/EMI/rail voltages не перенастраиваются; корректность холодного аппаратного состояния ими не доказана.

Unicorn — CPU/RAM плюс описанные MMIO-фикстуры, не цифровой двойник MT6261. Наличие BootROM USB само по себе не доказывает достижение MAUI и не исключает более раннюю аппаратную проблему.
