**Дата:** 16 ноября 2026 года. **Режим:** только статическое чтение, без исполнения firmware и без доступа к устройству.

## 1. Главный результат и поправка к исходной точке

**`CPU 0x1003066C / file 0x3066C` — не функция, а начало ASCII-строки `hal\audio\src\v1\audio_service.c`.** Строка вместе с NUL занимает `[file 0x3066C, 0x3068D)`. Её Thumb-дизассемблирование даёт формально допустимые, но ложные инструкции. Делать из них MMIO-трассу нельзя.

Перед строкой действительно находится маленькая функция по `CPU 0x1003065C / file 0x3065C`: она передаёт эту строку и номер исходной строки в обёртку над callback. По дальнейшему коду это **allocator-like API, а не настройка ЦАП**. Второй экземпляр строки у `file 0x5C250` также привязан к software callback, не к установленной DAC-последовательности.

Независимо от ошибочной исходной точки удалось углубить **настоящую аудиоветвь**: дескриптор `L1Audio_HISR` → `0x10013668`, setup/event-loop `L1Audio` у `0x10013728`, программные таблицы callbacks, DSP/DPRAM-обращения и ARM-veneer в RAM-код `0xF024…`, `0xF02F…`, `0xF031…`. **Это отдельная подтверждённая зацепка, а не найденный вызов из строки `0x1003066C`.**

**Итог по ЦАП:** в протрассированных участках **нет операций, которые можно уверенно назвать включением DAC, подачей PCM, выбором sample rate или настройкой аналогового выхода**. Есть точные audio-related обращения к DPRAM/MMIO; их нельзя повышать до статуса DAC. Сквозной путь PCM → DSP/AFE → аналоговый выход пока не восстановлен.

## 3. Что реально находится около `0x1003066C`

### 3.1. Ближайшая функция `0x1003065C` — allocator-like, не AFE [E01–E03]

| CPU / file | Наблюдение | Статус |
|---|---|---|
| `0x1003065C / 0x3065C` | `PUSH {r4,lr}` | D |
| `0x1003065E / 0x3065E` | `LDR r2,[PC,#8]`, pool `file 0x30668` = `0x000006A4` (1700) | D |
| `0x10030660 / 0x30660` | `ADR r1,…` → ровно `0x1003066C` | D |
| `0x10030662 / 0x30662` | `BL 0x10038DA8` | D |
| `0x10030666 / 0x30666` | возврат; дальше literal, затем строка | D |

`0x10038DA8` сохраняет входной `r0` как размер, при нуле возвращается; иначе загружает таблицу `T = 0xF005922C` (literal `file 0x38DC8`), вызывает `BLX [T+4]`, а при ненулевом результате обнуляет полученный блок длиной, равной исходному `r0`, через `0x100429F0`. ARM-код `0x100429F0` явно пишет нулевые байты/halfwords/words в переданный адрес.

**D:** вызов provider в ячейке `0xF0059230` и обнуление результата. **I, высокая:** zero-initializing allocation с file/line tracking. Строка `audio_service.c` говорит о вызывающем исходном модуле, а не превращает allocator в аудиорегистр. Значение `0x6A4` — передаваемый номер строки, не коэффициент DAC.

**Неразрешённый хвост:** фактический указатель `[0xF0059230]` в этом исследовании не восстановлен. Назначать этому callback имя DAC-функции нельзя. В просканированных кандидатах прямых ARM/Thumb-вызовов исходной обёртки в основном коде входящего ребра не найдено; абсолютного raw-указателя `0x1003065C`/`0x1003065D` во всём образе тоже нет. Это не исключает вызов из распакованного кода или вычисляемый адрес.

### 3.2. Вторая строка и другая обёртка [E04–E06]

- Функция `CPU 0x1005C23C / file 0x5C23C` кладёт `r0` на стек, задаёт `r2 = 0x6A9` (1705, pool `file 0x5C24C`), `r1 = 0x1005C250`, `r0 = sp`; вызывает `0x1003E000`.
- `0x1003E000` загружает **другой** callback `[0xF005922C+8] = [0xF0059234]` и делает `BX`. Его реализация/точная семантика неизвестны. Интерфейс с адресом локального слота согласуется с освобождением/управлением памятью, но **это только гипотеза**, не восстановленное имя `free`.
- Существует абсолютный Thumb-указатель `0x1005C23D` в pool `file 0x294AC`. `CPU 0x10029470` загружает его в `r1`; `0x10029474` кодирует `BL 0x1036EDF8` с `r0 = 1`. По `file 0x36EDF8` в текущем NOR стоят `FF`. Поэтому не объявляю это доказанной runtime-регистрацией или реально доступной функцией: исполняемое отображение этой цели не установлено.

Ни в одной из этих коротких обёрток нет установленного доступа к AFE/DAC.

## 4. Настоящая аудиоветвь: `L1Audio` и HISR

### 4.1. Надёжные входные зацепки [E07–E10]

**Дескриптор HISR**, `file [0x61F40,0x61F50)`:

| file | Значение | Что доказано |
|---|---|---|
| `0x61F40` | `0x00010108` | первый байт — логический ID `8`; остальные поля здесь не названы аппаратными IRQ |
| `0x61F44` | `0x00000300` | raw-поле; это не доказанный размер PCM/DMA-буфера |
| `0x61F48` | `0x10013669` | Thumb-entry `CPU 0x10013668` |
| `0x61F4C` | `0x1009A348` | строка `L1Audio_HISR` в `file [0x9A348,0x9A355)` |

Связь не ограничена похожей строкой: `0x10013734` задаёт ID `8`, `0x10013736` вызывает `0x10037BC8`; та процедура действительно ищет запись по первому байту в таблице `0x10061F20`, с шагом `0x10`, и передаёт указатель entry/name дальше в `0x10012E78`. Поэтому связь `L1Audio setup → HISR ID 8 → 0x10013668` подтверждена статически. **ID 8 — индекс software-дескриптора, не восстановленный номер аппаратного аудио-IRQ.**

У `CPU 0x10013728 / file 0x13728` есть setup и бесконечный event-loop. `0x1001372A` делает `ADR r0` на строку `L1Audio` по `0x10013844`. Через pool `file 0x1384C` используется общий контекст **`C = 0xF005925C`**. Именование процедуры `L1Audio setup/event-loop` — I по строке и структуре; её непосредственный caller/запись планировщика здесь не восстановлены.

### 4.2. Программные callback-таблицы, не PCM FIFO [E10, E13–E17]

Удалось согласовать записи и чтения одного контекста:

| Поле относительно C | Адрес/размер группы | Установленное использование |
|---|---|---|
| `C+0x1C` | `0xF0059278` | handle, возвращённый созданием/получением HISR по ID 8 |
| `C+0x20+4*i`, `i<18` | `0xF005927C…` | callbacks task-loop; setter `0x1005A110`, косвенный вызов `0x1001382E` |
| `C+0x68+4*i`, `i<18` | `0xF00592C4…` | аргументы task-loop; setter/poster `0x10034484` |
| `C+0xB8+4*i`, `i<5` | `0xF0059314…` | callbacks HISR; запись в `0x1005B8CC`, вызов `0x100136A8` |
| `C+0xCC+2*i`, `i<5` | `0xF0059328…` | 16-битные ID пяти HISR slots |
| `C+0xD8+4*i`, `i<5` | `0xF0059334…` | аргументы для пяти HISR callbacks |
| `C+0xEC` | `0xF0059348`, 16 бит | pending mask пяти HISR slots |
| `C+0xB4` | `0xF0059310`, 32 бита | pending mask для 18 task events |

`0x1005B8CC` ищет свободный ID среди пяти слотов, записывает ID/callback/argument. `0x1001C3E4` ищет совпадающий ID, ставит бит в `C+0xEC` и вызывает software-механизм активации по handle `C+0x1C`. HISR `0x10013668` очищает биты и вызывает зарегистрированные функции; затем передаёт 18-slot события в task через `0x10034484`. В task-loop `0x10013828–0x1001382E` загружаются аргумент и callback, после чего выполняется `BLX r1`.

**D:** это реальные таблицы указателей и событий. **Не установлено:** какие callbacks отвечают именно за PCM downlink, их фактические RAM-значения на работающем устройстве, адрес/формат аудиобуфера. Числа 5 и 18 — количества software slots, а не DMA channels, sample width или размеры блоков.

### 4.3. DSP-command bridge [E15]

`CPU 0x1001B84C / file 0x1B84C` сохраняет входное 16-битное значение в `C+0x0E`, сохраняет timestamp в `C+0x10`, выполняет одну MMIO-запись (ниже), вызывает RAM-процедуры через veneer и далее:

- `0x1001B8A2` / `0x1001B8CE` → `0x1001C3E4` для dispatch по ID;
- в fallback сохраняет значение в `C+0x0C`, затем вызывает `0x1003B6F4` с HISR handle.

**I:** мост DSP/аудиособытия в `L1Audio_HISR`. Конкретный hardware-IRQ, точный формат команд и смысл отдельных значений не установлены. Это ещё не поток PCM и не запись в DAC.

Эта подзадача не использует ранее созданные непроверенные производные распаковки как исполняемый код. Полная распаковка/восстановление runtime image не выполнялись.

### 5.2. Одну RAM-ветвь всё-таки удалось пройти до конца [E22–E24]

`0x10013814` (а также `0x1001B854`) → veneer `0x10036E38` → Thumb `0x000012C8`.

Это не непроверенное сопоставление по младшим битам: startup у `CPU 0x1005D568–0x1005D57C` явно копирует `0x1120` байт из `0x1009A710` в `0x00000200`. Поэтому:

- `file 0x9B7D8` → `CPU 0x000012C8`: `PUSH; BLX 0x00000BA4; POP`;
- `file 0x9B0B4` → `CPU 0x00000BA4`: ARM-veneer на Thumb `0x100426AC`;
- `0x100426AC` читает 32 бита из **`0xA0180088`** (`LDR` в `0x100426B6`, pool `file 0x426F4` = `0xA0180080`), накапливает дельту в RAM и масштабирует результат.

**D:** полный статический путь и чтение MMIO. **I:** общий timestamp/timebase. Это **не подтверждённый счётчик проигранных аудиосэмплов**. Размещение вызова в аудио-loop не делает его sample clock.

## 6. Подтверждённые MMIO/DPRAM-последовательности — и что они НЕ доказывают

| CPU instruction / file | Операция | Literal pool | Классификация |
|---|---|---|---|
| `0x10021E7C / 0x21E7C` | `STRH 0xFFFF → 0x82207410` | `file 0x21E8C` = `0x82207400` | D: запись в обёртке входа HISR. R: окно DPRAM по reference. Назначение битов/полярность mask неизвестны |
| `0x1001367C / 0x1367C` | `LDRH ← 0x82207E56` | `file 0x13724` = `0x82207E40` | D: чтение перед callback-dispatch при ненулевом pending mask. Возможны status/synchronization; это гипотеза, не DAC FIFO |
| `0x1001B872 / 0x1B872` | `STRH 1 → 0x82CA007C` | `file 0x1B8F0` = `0x82CA0060` | D: запись в DSP-command bridge. ACK/handshake возможен, но точное имя регистра/бита не установлено |
| `0x100426B6 / 0x426B6` | `LDR 32-bit ← 0xA0180088` | `file 0x426F4` = `0xA0180080` | D: timestamp-ветвь; не доказанный DAC/sample counter |

Последовательность в HISR: software-обёртка с записью `0xFFFF` → проверка pending mask → чтение `0x82207E56` → очистка software-бита и косвенный callback → дальнейший dispatch → выходная обёртка с RAM-хвостом. Точные значения callbacks не восстановлены; без них нельзя дорисовать «подачу следующего PCM-блока».

**Подтверждённых DAC-операций в этой трассе: 0.** Подтверждённый DSP/DPRAM доступ не равен DAC, audio DMA или analog power-up. Нет доказанного `DAC enable`, `PCM FIFO write`, `sample-rate set`, `mute/unmute`, `speaker/headphone routing`, DAC gain или запуска audio DMA.

Результаты поиска в исходном NOR:

1. В primary-области `file [0,0xA28B0)` **нет 4-byte-aligned слов** ни из `0x82CD0000…0x82CDFFFF`, ни из `0xA0720000…0xA072FFFF`.
2. Кандидатный поиск Thumb16 `LDR [PC,imm]` в `file [0xB5B0,0x5D50C)` также не дал literal-доступов к этим окнам. Это поиск конкретной формы адресации, не полная символьная эмуляция.
3. Во всём образе есть 8 aligned-слов из первого полного 64-KiB окна и 13 из второго, но **все вне primary-области**, в упакованных/неподтверждённых данных. Это не MMIO-xrefs. Сканирование всех byte alignments нижних 4 KiB даёт отдельные случайные совпадения; список сохранён в E26.
4. Особенно нагляден ложный ABB-кандидат у `file 0x5F203`: четыре байта дают `0xA07206E1`, но они пересекают границу ARM-инструкций `LDRH`/`LSL`, а не являются literal pool.

**Отсутствие этих literals не доказывает отсутствия AFE в firmware.** База может вычисляться, передаваться через RAM или находиться внутри распаковываемого кода. Здесь отрицательный результат только не позволяет подтвердить reference-адреса по наблюдённым MMIO.

Есть и **конфликт карт из references**: старые `AFE_VAG_CON/AFE_VAC_CON…` в `afe.h` используют `MIXED_BASE+0x100`, тогда как Fernly называет `0xA0170100` `MPLL_CON0`. Boot-код по `0x10009166`/`0x10009184` действительно читает `0xA0170100`, выделяет шестибитное поле и сравнивает с `0x18`/`0x14`; затем настраивает `0xA001011C`/`0xA0010108`. Превращать это чтение в DAC gain на основании одного совпавшего адреса нельзя; аудио-reachability для него нет.

`afe.c` пригоден для гипотез о типах блоков, но не как восстановленная последовательность Kenshi. Например, `BeepHz` прямо содержит эмпирическое предположение о внутреннем делителе `N=32`. Ни эта частотная формула, ни функции `AFE_initialize`/`AFE_EnsureOutputPath` не являются доказательством из дампа. Их код не переносился и не запускался.

## 8. Что осталось неизвестным и точное продолжение read-only анализа

1. **RAM-код AFE:** восстановить проверяемое отображение/распаковку прежде всего для entries `0xF0247B08`, `0xF0247C00`, `0xF0247CFC`, `0xF02F8B5A`, `0xF02F95D4`, затем выходного хвоста `0xF03116B4`. Отслеживать literal pools и вычисление баз уже в достоверных RAM-байтах. Без этого имя «AFE-init» остаётся гипотезой.
2. **Callbacks:** установить реальные записи в `C+0xB8`, `C+0x20`, provider `T+4/T+8`; связать конкретные функции с PCM downlink, а не с общим DSP/GSM/audio dispatch. Текущие таблицы содержат адреса функций/аргументы, а не найденные PCM samples.
3. **Данные/тайминг:** неизвестны PCM/DSP buffer addresses, ring layout, sample width, mono/stereo, поддерживаемые частоты, реальный счётчик потребления samples, DMA descriptors и hardware IRQ. ID HISR `8` и поле `0x300` их не заменяют.
4. **Аналоговая часть:** не установлены clock/power/reset, DAC gain/mute, de-pop, выбор динамик/наушники, внешний amplifier-enable и соответствие ревизии SoC/платы.
5. **Память/отключение GSM:** из найденного DSP-пути нельзя заключать, что допустимо выключить общие DSP/clock domains; доступ audio DMA к SRAM/TCM не доказан.

Никакого аудиодрайвера, тестового тона или записей MMIO не создавалось и не выполнялось. Исходный дамп, helper, references, существующие отчёты, repo/проект не редактировались; новые материалы этой подзадачи — только этот файл и приложение E01–E27.
