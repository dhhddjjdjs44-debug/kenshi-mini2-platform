Дата: 16 ноября 2026 года. Подзадача выполнена статически и read-only по отношению к исходным материалам. Драйвер не реализован, другие агенты не запускались, операции на устройстве не выполнялись.

## 1. Краткий результат и границы достоверности

- **Подтверждён SD pinmux в общей GPIO-инициализации:** GPIO31 = MCCK, GPIO32 = MCCM0, GPIO33…36 = MCDA0…3, везде mode **1**. Это следует из фактической таблицы в дампе и фактического цикла записи, а не только из datasheet.
- **Подтверждён адрес VMC:** `VMC_CON0 = 0xA07001C0`. В дампе есть две записи rail-таблицы с этим адресом и две копии кода прямого 16-битного RMW этого регистра.
- **Прямой RMW VMC устанавливает только `0x0800` (bit 11).** Он **не** устанавливает `RG_VMC_EN` (bit 0), **не** выбирает `VMC_ON_SEL` (bit 1) и **не** задаёт `RG_VMC_VOSEL` (bits 6:4). Называть его «включением VMC на 3,3 В» нельзя.
- **Не подтверждена сквозная цепочка «SD power-on → выбранный VMC rail → EN/VOSEL → выдержка стабилизации».** Универсальный PMIC-setter восстановлен, но SD-специфические входные аргументы и runtime-mapping, выбирающие именно VMC, не восстановлены. Напряжение VMC, режим управления и последовательность включения/выключения слота остаются **неизвестными**.

Это **порядок инструкций на указанной ветви**, а не доказанная полная последовательность подачи питания на слот.

### 3.1. I/O-контроллер: подтверждённые маски, неизвестное начальное значение

Функция file `0xF7A0` / CPU `0x1000F7A0` (`E07`) использует base `0xA0130000`, literal file `0xF7E0`. Её записи:

- file `0xF7B4`, CPU `0x1000F7B4`, `STR` в **MSDC_IOCON `0xA0130014`**: сохраняет bits31:8 старого значения, bits7:0 заменяет младшим байтом результата `BL 0x10251B78` (call file `0xF7AA`, bytes `42 f2 e5 f9`).
- file `0xF7BE`, CPU `0x1000F7BE`: `MSDC_IOCON |= 0x00280000` (`5 << 19`).
- file `0xF7CE`, CPU `0x1000F7CE`: `MSDC_IOCON = (MSDC_IOCON & ~0x03000000) | 0x01000000`.
- file `0xF7DC`, CPU `0x1000F7DC`: **MSDC_IOCON1 `0xA0130018` = `0x00022222`** (literal file `0xF7E8`).

**Не восстановлен результат `0x10251B78`.** Нельзя подставлять вымышленный low byte IOCON или утверждать точную начальную drive/slew-конфигурацию. Номинальные байты raw file `0x251B78` не приняты за код этой runtime-функции: отображение упакованного компонента не восстановлено (`E21`).

Важно: маска `0x00280000` применяется к **IOCON** `0xA0130014`, а не к **CFG** `0xA0130000`. Совпадение номера bit21 не делает эту запись управлением VDDPD/VMC. В datasheet у MSDC_CFG bit21 есть название VDDPD; это не подтверждает управление VMC через данную IOCON-запись или через разводку платы.

### 3.2. Reset/часть подготовки — не PMIC

`0x100373E4` (`E08c`) выполняет 32-битный RMW `MSDC_CFG |= 2`, проверяет bit1 и, при превышении разницы счётчика `2`, выполняет `MSDC_CFG &= ~2`. Единицы времени счётчика здесь не установлены; это **не задержка стабилизации VMC**.

`0x100117A0` (`E08a`):

- file `0x117AA`: `MMIO32[0xA0130080] &= ~0x80`;
- file `0x117B6`: через `0x10037754` задаёт field mask `0xFF000000` регистра `0xA0130020` значением `0x50` (результат `(old & ~0xFF000000) | 0x50000000`);
- file `0x117C2`: `MMIO32[0xA001010C] |= 1`;
- file `0x117CE`: `MMIO32[0xA0130000] &= ~0x18`;
- file `0x117DA`: вызывает `0x10013E9C` с `r0=0xF0`, то есть дальнейшую настройку SD clock divider. Не приписываю этому значение напряжения питания.

Общий field-writer `0x10037754` прочитан (`E08d`): `(old & ~mask) | (value << ctz(mask))`; дополнительного ограничения shifted value маской в нём нет. Приведённые выше конкретные аргументы помещаются в соответствующие поля.

`0x1003BE00`, вызываемый из SD init, формирует сервисный запрос: byte0=`0x12`, word по `+4`=`1`, команда `r1=2`; сам wrapper не пишет `VMC_CON0` (`E12a`). Само наличие `0x12` **не связывает** запрос с rail-id `0x12` из другой таблицы: пространства идентификаторов и конечный обработчик должны быть доказаны отдельно.

## 4. VMC/PMIC: что действительно найдено в дампе

### 4.1. Четыре буквальных вхождения `0xA07001C0`

Поиск little-endian слова по всему дампу с шагом 2 (`E18`) дал:

| File слова | CPU-адрес слова | Роль |
|---|---|---|
| `0x00004270` | `0x10004270` | Literal прямого RMW в BL2-функции `0x1000414C` |
| `0x00008560` | `0x10008560` | Поле base в BL2 rail-записи, начало записи file `0x855C` |
| `0x00010BF4` | `0x10010BF4` | Literal прямого RMW в main-функции `0x10010AD0` |
| `0x0006D350` | `0x1006D350` | Поле base в main rail-записи, начало записи file `0x6D34C` |

Обе rail-записи имеют слова `{0x00000012, 0xA07001C0, 0x00000000}`. Это **данные, не инструкции записи питания**.

Значение `0xA07001C4` как выровненный на 2 байта literal не найдено. Это не доказательство отсутствия обращений к VMC_CON1: адрес может получаться как `base+4`.

### 4.2. Прямые операции: только установка bit11

| File кода | CPU кода | Операция |
|---|---|---|
| `0x416C…0x4174` | `0x1000416C…0x10004174` | Загрузить literal `0xA07001C0`, `LDRH`, `BIC #0x0800`, `ORR #0x0800`, `STRH` |
| `0x10AF0…0x10AF8` | `0x10010AF0…0x10010AF8` | Та же последовательность |

`r3=0x0800` получен из `1 << 11`, `r2=r3` (`E09b/c`). Эквивалент обеих последовательностей:

`MMIO16[0xA07001C0] = (old & ~0x0800) | 0x0800`.

Результат — установка bit11 с сохранением остальных прочитанных битов. В локальном описании VMC_CON0 этот bit не назван среди EN/ON_SEL/VOSEL, и смысл ему не присваивается.

BL2 caller подтверждён: file `0x330C` / CPU `0x1000330C` вызывает `0x1000414C` **при нулевом результате** предыдущего вызова `0x10005C74` (`E09a`). Связь этой общей PMIC-настройки с SD и фактическое выполнение данной ветви при конкретной загрузке не доказаны. Для `0x10010AD0` прямой caller в выполненном Thumb-скане несжатой части не найден; это не означает «никогда не вызывается».

Следующая инструкция загрузки VMC base (file `0x4176` / `0x10AFA`) затем делает `base += 0x60` и обращается по `+0x1C`: фактический адрес **`0xA070023C`**, уже **не VMC_CON0/1**. Нельзя присоединять последующие PMIC writes к VMC только из-за повторной загрузки этого literal.

По локальному datasheet (`E20`):

- VMC_CON0 bit0 — `RG_VMC_EN`;
- bit1 — `VMC_ON_SEL` (software EN при 1; аппаратный путь при 0);
- bits6:4 — `RG_VMC_VOSEL`;
- bit10 — `RG_VMC_NDIS_EN`;
- bit15 — status.

Найденный `0x0800` не совпадает ни с EN, ни с ON_SEL, ни с полем выбора напряжения. Reset defaults datasheet не используются как значения, выбранные прошивкой Kenshi Mini 2.

### 4.3. Восстановлен общий механизм PMIC setter, но не SD-выбор rail

Функция file `0x13060` / CPU `0x10013060` (`E10a`):

1. Читает `index = MMIO/RAM8[0xF00A835E + r0]` — **RAM**, не ROM.
2. Выбирает `base = ROM32[0x1006D2E0 + index*12 + 4]`.
3. Вызывает `0x1003635C`, сохраняя входные `r1=field_index`, `r2=value`.

У rail-таблицы stride=12; VMC — запись **index 9**, file `0x6D34C`, CPU `0x1006D34C` (`E16`). Наличие в первом слове записи числа `0x12` само по себе не доказывает `RAM8[0xF00A835E+logical_id] == 9` для SD-запроса.

Общий setter file `0x3635C` / CPU `0x1003635C` (`E10b`):

- field-table base `0x1006D37C`, stride=6;
- byte `+1` = byte-offset регистра относительно rail base;
- halfword `+2` = mask;
- byte `+4` = shift;
- чтение `LDRH` file `0x36370`, запись **`STRH` file `0x3637E`**, CPU `0x1003637E`;
- значение: `(old & ~mask) | ((value << shift) & mask)`.

Вокруг RMW есть вызовы `0x1000C068` / `0x1000C060`; сам факт вызовов подтверждён, отдельное поведение этих служебных функций здесь не переопределяется.

| Индекс поля | File / CPU записи таблицы | Offset | Mask | Shift | Что следует из данных |
|---|---|---|---|---|---|
| `0` | `0x6D37C` / `0x1006D37C` | `0` | `0x0001` | `0` | При выборе VMC меняет его bit0 |
| `1` | `0x6D382` / `0x1006D382` | `0` | `0x0002` | `1` | При выборе VMC меняет bit1 |
| `3` | `0x6D38E` / `0x1006D38E` | `0` | `0x01F0` | `4` | Общее 5-битное поле; не объявляется безусловно VMC VOSEL |
| `5` | `0x6D39A` / `0x1006D39A` | `0` | `0x0800` | `11` | Общее поле bit11 |
| `0x12` | `0x6D3E8` / `0x1006D3E8` | `0` | `0x0070` | `4` | Маска совпадает с VMC VOSEL, но SD caller с этим полем не установлен |

**Два разных `0x12`:** rail-id в 12-байтной таблице и индекс поля в 6-байтной таблице — разные сущности. Их нельзя отождествлять.

Диспетчер file `0x106E8` / CPU `0x100106E8` читает logical rail из byte0 входной структуры (`E11a`). Проверены ветви:

- команда `2`: `r2 = word[input+4]`, field `0`, общий переход к call file `0x107A2`;
- команда `0x1FB`: `r2 = byte[input+1]`, field `1`, тот же общий call;
- команда `0x1FA`: `r2 = byte[input+1]`, field `2`, тот же call;
- команда `4`: сначала lookup через `0x100354F8`, затем field `3` и call file `0x1073A`; следом `0x10033730` (`E11b/c`).

Для выполнения VMC enable посредством этого маршрута нужны как минимум доказанные logical rail, runtime-mapping к index9, команда/field и value. Их SD-специфическое сочетание **не установлено**, поэтому таблица setter не превращается в утверждение о включении VMC.

`0xF00A835E` попадает в startup zero-область `0xF00541E4…0xF014CA70`: операция zero вызывается file `0x5D67C` / CPU `0x1005D67C` с размером `0xF888C` (`E13`, также проверен существующий scatter). Нельзя принять первоначальные нули BSS за рабочую инициализированную PMIC mapping-таблицу. Заполняющий её этап в этой подзадаче не восстановлен.

### 4.4. Что не следует путать с VMC

- `0xA0700A00`, объявленный `PMIC_ADDR` в локальном `fernly-fernvale-pmic.h`, **не** равен `VMC_CON0 = 0xA07001C0`.
- Wrapper file `0x37420` / CPU `0x10037420` действительно вызывает общий PMIC-setter с base **`0xA0700A00`**, file call `0x37428` (`E12b`). Это не основание назвать его VMC enable.
- MSDC reset, GPIO mode, controller clock divider, IOCON и service request с byte `0x12` не заменяют доказанного PMIC EN/VOSEL-пути.

## 5. Что подтверждено и что остаётся открытым

| Вопрос | Статус |
|---|---|
| MSDC0 base `0xA0130000` | **Подтверждено** literal и MMIO инструкциями |
| SD alternate mode GPIO31…36 | **Подтверждено** ROM-таблицей и общим write-loop |
| GPIO_MODE3/4 значения | **Подтверждено:** `0x11111101` / `0x11111111` |
| Специальные SD pull R0/R1 на общем init-этапе | **Подтверждено:** relevant R0=R1=0; последующие изменения/внешние резисторы неизвестны |
| Полный начальный low byte MSDC_IOCON | **Не подтверждено:** результат `0x10251B78` не восстановлен |
| MSDC_IOCON1 write | **Подтверждено:** `0x00022222` |
| VMC register base | **Подтверждено:** `0xA07001C0`, не `0xA0700A00` |
| Прямая VMC операция | **Подтверждено:** 16-битная установка `0x0800`; не EN/VOSEL |
| Универсальный PMIC RMW | **Подтверждено:** 16-битный table-driven setter |
| Какой logical PMIC id выбирает SD и чему равна его runtime mapping | **Не подтверждено** |
| SD действительно устанавливает RG_VMC_EN/ON_SEL/VOSEL | **Не подтверждено** |
| Реальное напряжение VMC слота | **Не установлено**, не выводилось из defaults/типичных схем |
| Порядок power-off → voltage → power-on, задержки и discharge | **Не установлен** |
| Наличие/подключение VDDPD к VMC на плате | **Не установлено** |
| Фактический card-detect GPIO/полярность, режим питания отсутствующей карты | **Не установлены**; SD callback boundary по slot `+0x60` отмечен в `E14`, но функция не названа по догадке |

### Ограничение отрицательных результатов

Поиск буквальных слов выполнен по всему дампу, прямых Thumb-call candidates — по несжатой области до file `0xA2CB0`. Проверены перечисленные тела функций и ветви; сплошной дизассемблированный поток, literal pool или совпадение байтов не принимались сами по себе за исполняемый код. Не восстановлены все косвенные callbacks, runtime-инициализация RAM mapping и упакованный компонент. Поэтому «цепочка не доказана» не означает «в прошивке нет такой цепочки».

**Практический итог анализа:** pinmux можно документировать как подтверждённый статический факт штатной общей инициализации. Для VMC пока допустимы только адрес регистра, буквальный RMW bit11 и общий механизм PMIC setter. Рабочие EN/VOSEL, напряжение и задержки для будущего SD-драйвера из этих данных назначать нельзя.
