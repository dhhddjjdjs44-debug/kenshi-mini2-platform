# Kenshi Mini 2 / The Night Shift — шаг 2: XIP-диагностика

**Дата:** 16 ноября 2026 года.  
**Статус:** проект создан; компиляция, упаковка и офлайн-проверки выполнены. **На телефоне не запускался и не прошивался.** Это bring-up образ, а не подтверждённая рабочая прошивка и не порт игры.

## 1. Что поставлено

- Freestanding C99 + небольшой ARM startup; ISA **ARMv5TE**, ARM-режим, без Cortex-M/Thumb-2/VFP. У GCC 14.2 нет имени CPU `arm7ej-s`, поэтому используется поддерживаемый `-march=armv5te`, покрывающий нужные инструкции без Jazelle.
- `Makefile` для `arm-none-eabi-gcc`, linker script, генератор GFH, read-only извлечение board-template из проверенного дампа. Есть Python-вариант сборки для Windows без установленного GNU Make.
- Собственные reset/vector/trap-обработчики, TCM-стеки, WDT disable, remap RAM; резерв 32 КиБ кэша, PSRAM-framebuffer и 8 КиБ DMA-резерва, linker ASSERT на 2 МиБ heap.
- Диагностика полного 4-МиБ окна PSRAM, LCD ID/профили B–C–A, CPU/PIO RGB565, собственный небольшой 8×8 шрифт, цветные полосы и hex-вывод четырёх keypad-регистров и инвертированной 64-битной маски.
- Дополнительная статическая дотрассировка SD/VMC и аудио. Рабочие SD/аудио-драйверы не подменены заглушками, выдающими успех: они в этом образе **не включены**.

Структура проекта (после распаковки):

```text
kenshi_step2/
  Makefile
  README_RU.md
  requirements-test.txt
  linker/mt6261.ld
  include/{board,psram,lcd}.h
  src/startup.S
  src/{boot,board,psram,lcd,main}.c
  src/{font,lcd_profiles}.inc
  board/lcd_profiles.json
  tools/{build,extract_board,gfh,gen_lcd_profiles,check_image,check_heap_assert,fs}.py
  tests/test_packaging.py
  tests/{emulate_psram,emulate_startup}.py
  docs/                 # трассировки, свидетельства, сведения об инструментарии
  build/                # MAUI-only BIN, ELF, MAP, проверенная карта и протоколы
```

Игра не интегрирована: это отдельный аппаратный диагностический проект. Исходники The Night Shift по указанному пути дампа не предоставлены. Никакие stock MMI/RTOS/modem callbacks из новой программы не вызываются; это замена приложения, а не вырезание байтов из связанного MAUI.

## 2. Что проверено сборкой

Проверено **настоящим GCC/ld**, а не только разбором исходников:

- Arm GNU Toolchain **14.2.Rel1**, `gcc 14.2.1 20241119`; архив проверен по опубликованному SHA-256. Инструментарий размещён только в рабочем каталоге чата, не установлен глобально и не включён в архив проекта.
- Положительная сборка через Python и через **GNU Make 4.4.1**, включая принудительное пересоздание объектов (`make -B`). Предупреждения компилятора/линкера считаются ошибками. ELF: little-endian ARMv5TE; неразрешённых символов нет.
- **11/11** тестов упаковки: цепочка GFH, смещения, подпись=0, неправильный entry, повреждённый заголовок, пустой/невыровненный/слишком большой payload, логическая сохранность защищённых диапазонов и происхождение LCD-данных.
- **Отрицательный linker-тест:** добавление `0x200000` байт `.bss` действительно заканчивается ошибкой `Continuous heap smaller than 2 MiB`. Проверено требуемое ASSERT, а не произвольная ошибка инструментария.
- Исполнена **реальная скомпилированная функция `psram_test()`** в ARM-эмуляторе: 4 МиБ проходит; 2-МиБ и 1-МиБ зеркалирование обнаруживается; stuck-low bit0 обнаруживается. Зеркалирование моделируется общим backing storage, не отдельными независимыми копиями RAM.
- Отдельно выполнен startup до входа в `diagnostic_main`: первая MMIO-запись — WDT `0x2200`; banked stacks выставлены; 64 байта векторов скопированы; `.data` и `.bss` инициализированы; IRQ/FIQ остаются замаскированы.

**Граница эмуляции:** это тест инструкций и программного порядка. В startup-тесте MMIO — простая модель регистров, а cache-command искусственно auto-clear. Настоящие EMI, кэш, MPU, BL2, LCD, DMA и PMIC не эмулируются. Эти проверки **не подтверждают работу на MT6261** и не измеряют физическую RAM телефона.

## 3. Образ и GFH

| Поле | Значение |
|---|---|
| Файл | `build/kenshi_diag_maui.bin`, только замена MAUI, не полный NOR |
| Логическое смещение начала | `0x00B000` |
| Конец диапазона, не включительно | `0xd0e8` |
| Размер BIN с GFH | **8424 байт = 0x20e8** |
| load_address | `0x1000B000` |
| entry / Reset_Handler | `0x1000B5B0` |
| FILE_INFO file_type | `0x0100` |
| content_offset / jump_offset | `0x5B0` / `0x5B0` |
| signature_type / signature_length | `0` / `0` |
| max_file_size | `0x37E000` — ограничено началом системного хвоста |
| Не затрагиваемые логические диапазоны | `[0x0,0xB000)` и `[0x389000,0x400000)` |

SHA-256 подготовленного BIN:

```text
bb2bed62f7c6a83698d58a91bf276febfde13fd48a1d007703a7b0217f9c0ca6
```

Заголовок длиной `0x5B0` формируется из **ровно идентифицированного исходного dump-template**, а не выдуманной структуры. Сохраняется вся цепочка семи GFH-записей и исходная board metadata; в FILE_INFO обновляются фактическая длина и разрешённый максимум. Подпись/длины/entry проверяются, входные файлы не перезаписываются. Файл `flash-plan.json` фиксирует байтовые границы, entry и SHA-256; это **описание образа, не команда программатору**.

**Важно:** остальные GFH-записи сохранены как opaque stock metadata, включая прежние идентификационные строки и memory-related сведения. Их полная семантика в BL2 и принятие нового размера приложения **не доказаны**. Структурно корректный GFH не означает аппаратно подтверждённый handoff BL2. На этом шаге не выполнялись обход проверок, изменение ARM_BL/ARM_EXT_BL или новая подпись загрузчиков.

### Физическое стирание — отдельное обязательное условие

Границы в таблице относятся к **байтам файла**, не к erase-секторам NOR. Если конкретная NOR/программатор стирает только 64-КиБ блок, участок `0xB000` попадает в блок `[0x0,0x10000)` вместе с загрузчиками. Поэтому нельзя честно обещать «загрузчики не тронем» одной лишь упаковкой BIN. До записи нужны подтверждённые JEDEC ID, erase geometry и способ сохранения/восстановления соседних байтов; автокоманда flash/erase намеренно отсутствует. Образ не дополнен до размера всего NOR и ничего не пишет сам.

## 4. Фактическая linker-карта этого диагностического ELF

Все интервалы справа открыты. `0xF0000000+` — алиас той же PSRAM, не дополнительная память.

| Область | Физические/логические адреса | Размер / назначение |
|---|---|---|
| ARM vectors reserve | `0x00000000–0x00000100` | 256 байт; копируется `0x40` байт из `0x1000B640` |
| DMA reserve | `0x00000100–0x00002100` | `0x2000` = 8 КиБ, NOLOAD, выравнивание 32 |
| Framebuffer | `0x00002100–0x0000C100` | `0xA000` = 40 КиБ, 128×160×2, выравнивание 32 |
| `.data` | `0x0000C100–0x0000C108` | 8 байт с выравниванием; cookie проверяет копирование |
| `.bss` с выравниванием | `0x0000C108–0x0000C120` | 24 байта |
| **Непрерывный heap** | **`0x0000C120–0x00400000`** | **`0x3F3EE0` = 4 144 864 байта ≈ 3,953 МиБ** |
| TCM cache reserve | `0x70000000–0x70008000` | 32 КиБ; не используется для C-данных/стеков |
| ARM-стеки | `0x70008000–0x70009C78` | отдельные банки; SVC nominal top `0x70009C74` |
| Диагностический mailbox | `0x70009C80–0x70009CB4` | 52 байта, NOLOAD; не лежит на рабочем стеке |
| Остальная TCM до `0x7000B000` | не выделена программе | не объявлена игровой кучей |

CPU работает с framebuffer через `0xF0002100`; DMA-резерв имеет CPU-алиас `0xF0000100`. **Реальный DMA не запускается:** применимость этих alias-адресов в регистрах DMA, в отличие от CPU-адресации, пока не подтверждена. Будущий bus/DMA address нельзя автоматически приравнивать к CPU uncached pointer.

Код и константы — XIP. Нет переносимого в PSRAM текста, RTOS, malloc-аллокатора или динамических выделений. На этом шаге heap — непрерывная зарезервированная область с linker-символами; подключение единого malloc относится к интеграции игры. В `.heap` применён NOLOAD, поэтому `size` включает весь резерв в BSS — это **не 4 МиБ занятых runtime-данных** и не большой flash BIN.

Требуемая проверка в linker script:

```ld
ASSERT((__heap_end - __heap_start) >= 0x200000,
       "Continuous heap smaller than 2 MiB")
```

Также проверены entry, размер vector template, framebuffer, выравнивание, конец heap и отсутствие пересечения с системным хвостом NOR. Для будущей игры ASSERT гарантирует **размер арены**, а не всегда свободный malloc-блок после выделений/фрагментации.

## 5. Порядок старта и тест памяти

1. ARM entry выставляет SVC, маскирует IRQ/FIQ. **Первая MMIO-запись** отключает WDT (`0xA0030000`, 16 бит, `0x2200`).
2. Выставляются UND/ABT/FIQ/IRQ/SYS/SVC SP. Номинальное stock-значение SVC — `0x70009C74`; перед первым вызовом C оно выравнивается до **`0x70009C70`**, поскольку исходное значение не кратно 8. Внутри C SP далее закономерно уменьшается на размер frames.
3. Создаётся TCM-mailbox; выполняются cache/remap-настройки: alias `[0xF0000000,0xF0400000)`, MPU/cache region 0 для полного NOR-окна `[0x10000000,0x10400000)`, резерв 32 КиБ кэша. Конец region0 намеренно расширен с начального stock `0x10001000` до `0x10400000`; это новое значение, а не извлечённая готовая последовательность. Полная новая композиция cache-control и handshake остаются аппаратными предпосылками, а не результатом теста телефона. EMI/PLL/PMIC voltage не перепрограммируются: используется состояние после BL2.
4. **До создания runtime-данных** выполняется разрушительный тест всех `0x400000` байт PSRAM из XIP с TCM-стеком: walking data bits, address-line sentinels, уникальные по адресу шаблоны, инверсии, нули/единицы с прямым/обратным проходом. Он обнаруживает зеркалирование и базовые дефекты, но не заменяет длительный стресс-тест при разных частотах/питании.
5. Только после успешного теста копируются 64 байта векторов в physical `0x0`, инициализируются `.data/.bss`, затем запускается экранная диагностика. Первые 256 байт остаются исключены из heap.

Это необходимое изменение порядка относительно буквального «сначала .data, затем полные 4 МиБ»: иначе тест стёр бы векторы, framebuffer и собственные глобальные данные. Исполнение теста из действующей stock MAUI/RTOS запрещено архитектурой: он уничтожает всю RAM и не возвращается в загрузчик. Нужен холодный handoff BL2 без фонового DMA в тестируемую память. При отсутствующей памяти, дающей bus abort вместо зеркала, корректный вывод ошибки на LCD не гарантирован.

Коды `psram_test`: 1 — data bus, 2 — address alias, 3/4 — адресный шаблон/инверсия, 5/6 — нули/единицы. На ошибке нет обращения к framebuffer в неисправной PSRAM: используется PIO красно-белая индикация, подробности — в TCM-mailbox. Ошибка cache/remap (`0xC1`) останавливает старт раньше LCD.

## 6. LCD и кнопки

### LCD

- Контроллер SoC `0xA0450000`; command/data `0xA0450F80/0xA0450F90`, 16-битные записи. ID читаются **8-битными** чтениями, как в stock-коде.
- GPIO45…49 переведены в mode 1 по stock mode-table file `0x83668`; затрагивается только LCD-подмножество, не вся modem/SIM/camera GPIO-конфигурация. Восстановлены gate bits 0/7, serial timing/config и связанное регистровое поле из stock LCD-пути.
- Стоковая таблица выбора по file `0x9D4D0` и связи с профилями восстановлены точнее, чем на шаге 1:

| Профиль | Ключ ID | Как составляется |
|---|---|---|
| B | `0x7C89` | `(DA << 8) | DB` |
| C | `0x9106` | `(DB << 8) | DC` |
| A | `0x3300` | `(DA << 8) | DB` |

Таблица подтверждает критерии stock-программы, **не физически установленный чип**. При совпадении профиль фиксируется; при неизвестном ID выполняется циклический показ **B → C → A**, по 32 итерации main loop. Время не объявляется секундами. Изменение keypad-mask с нажатой клавишей после первого кадра фиксирует выбранный fallback; при постоянном нулевом/нерабочем keypad он продолжит цикл.

Инициализационные команды хранятся в JSON с file offsets и генератором `.inc`. Пиксельные clear-loops stock-прошивки не ошибочно включены как параметры последней команды. Задержки реализованы консервативным busy-loop с настраиваемым `DELAY_LOOPS_PER_UNIT`; **это не калиброванные миллисекунды**. Унаследованные частоты, физические bus timings, подсветка, byte/BGR/orientation на конкретной панели ещё требуют проверки.

Вывод сейчас CPU/PIO: окно `2A/2B/2C`, два 8-битных переноса на RGB565-пиксель. Это преднамеренно простой тест, **не быстрый DMA-blit**, не видеоплеер и не обещание FPS. Время полной перерисовки ограничивает частоту опроса кнопок в этом диагностическом приложении.

### Keypad

- GPIO12…21 — mode 1 из той же stock mode-table, только нужные pinmux/pull-поля.
- KP `0xA00D0000`; читаются `0xA00D0004/08/0C/10`. На LCD видны четыре сырых 16-битных значения и `~raw` как 64-битная hex-маска.
- Для теста выбраны документированные scan/debounce settings: `KP_SCAN_TIMING=0x11`, `KP_DEBOUNCE=0x100` (8 мс по формуле datasheet), double-keypad mode. Это **выбранные диагностические**, не объявленные восстановленными stock-значения.
- Физическая привязка цифр/D-pad/softkeys не навязана. Не включены KP_MEM5, power key через PMIC и полноценная обработка ghosting. Отображаются именно биты 0…63, не гарантированно все клавиши телефона.

## 7. Результат параллельной дотрассировки

### MSDC0 / VMC

Подтверждены mode 1 для **GPIO31…36** и общий GPIO-init write loop. Найден **VMC_CON0 `0xA07001C0`**, rail-table и прямой RMW. Но установленная прямая операция добавляет только **bit11 (`0x0800`)** — это **не** доказанная установка EN/VOSEL и не доказательство напряжения 3,3 В. Сквозная цепочка SD power-on → VMC rail → enable/voltage → стабилизация **не восстановлена**. Поэтому SD/PMIC-записей «наугад» в диагностическом образе нет. Подробности и конкретные file offsets встроены в приложения.

### Audio

Поправка к запрошенной точке: **`0x1003066C` — не функция, а строка `hal\audio\src\v1\audio_service.c`**. Ближайшая обёртка `0x1003065C` согласуется с allocation/callback path, не с настройкой ЦАП.

Независимо от этой ошибки протрассированы `L1Audio_HISR` → `0x10013668`, setup/event-loop `0x10013728`, callback-таблицы и veneer в RAM. Подтверждены audio-related обращения `0x82207410`, `0x82207E56`, `0x82CA007C`, **но назначать им смысл DAC без доказательств нельзя**. Дальнейший путь требует восстановления упакованных RAM-областей. PCM/DAC/AFE power-on, rate и DMA пока не установлены; аудио в BIN не заявлено работающим.

## 8. Как воспроизвести сборку

Нужны Python 3 и распакованный Arm GNU Toolchain с `arm-none-eabi-*` в PATH. Makefile проверен GNU Make 4.4.1. Исходный dump читается только для board-template, по умолчанию из переданного пользователем пути.

```powershell
# Выполнять из распакованного каталога проекта.
make check
# При другом пути к dump:
make check "DUMP=C:/path/to/kenshi_mini2_full.bin"
# Если GNU Make не установлен, эквивалентная проверенная сборка:
python tools/build.py --prefix arm-none-eabi- --dump C:/MTK_Drivers/dump_tool/kenshi_mini2_full.bin
# Отрицательный тест ASSERT:
make check-heap
```

Если compiler-prefix содержит путь с пробелами, Python builder передаёт его отдельным argv; Makefile также заключает compiler/objcopy/size в кавычки. `DUMP` рекомендуется передавать без пробелов, так как это также dependency GNU Make.

Для дополнительных, **не обязательных для компиляции**, ARM-эмуляционных проверок установите закреплённые `requirements-test.txt` в отдельное Python-окружение и выполните:

```powershell
make check-emu
# либо:
python tests/emulate_psram.py
python tests/emulate_startup.py
```

Локальная проверка этого чата использовала изолированные host-зависимости в рабочем каталоге, без установки пакетов в проект пользователя. В архиве нет compiler binaries, Python wheels, полного NOR и уникальных пользовательских данных системного хвоста.

## 9. Ограничения до аппаратного допуска

1. Подтвердить flash erase geometry и восстановление до записи, а не полагаться на логическое смещение `0xB000`.
2. Проверить принятие GFH/opaque MAUI metadata и новый handoff BL2. GFH FILE_INFO имеет заданные значения, но одной компиляции недостаточно.
3. Подтвердить фактические EMI, PSRAM 4 МиБ, cache/MPU/remap-композицию и ёмкость/доступность TCM выбранной ревизии; код не угадывает EMI timings.
4. Проверить LCD ID, тайминги/подсветку/ориентацию, стабильность PIO-цветов, физическую keypad-mask.
5. Проверить адресацию/когерентность реального DMA отдельно; текущий CPU-алиас не является доказательством доступности alias с периферийной шины.
6. Закрыть VMC power/voltage и реальный AFE/DAC path до SD/аудио HAL. Не отключать вслепую общие DSP/clock domains.

**Итог:** требования к структуре проекта, entry, C99-сборке, GFH-упаковке и 2-МиБ link-time heap реализованы и проверены офлайн. Готов диагностический кандидат для отдельного контролируемого bring-up, но аппаратный тест телефона ещё не выполнен. Шаг 3 — порт игры и полноценный медиа-HAL — не начат. Исходный dump и отслеживаемые файлы `dump_tool` не изменены.
