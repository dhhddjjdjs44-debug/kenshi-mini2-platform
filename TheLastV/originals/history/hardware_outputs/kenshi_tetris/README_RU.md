# Kenshi Mini 2 — тестовый «Тетрис» (C99, bare metal)

**Статус: собранный и проверенный офлайн кандидат. На физический телефон не записывался и на нём не запускался.** Предыдущий проект диагностики шага 2 и исходный полный NOR не изменены.

## Что есть

- Поле 10×20, семь фигур, генератор «мешок из семи», движение, поворот по часовой стрелке с простыми горизонтальными сдвигами у стены.
- Обычное и ускоренное падение, мгновенный сброс, удаление заполненных линий, счёт, следующая фигура, пауза и новая игра.
- RGB565-кадр 128×160. Первая передача полная, затем передаются только изменившиеся диапазоны строк; звука, SD и сетевого стека нет.
- Переназначение шести физических кнопок в RAM: распиновка именно этой клавиатуры ещё не измерена, поэтому номера клавиш не угадываются.
- Наследуется стартовый путь диагностики: WDT, ARM-стеки, настройки памяти, разрушительный тест PSRAM до инициализации векторов/данных, затем C99 main.

Это небольшой самостоятельный тест экрана и кнопок, **не порт «The Night Shift»**, не реализация полного FAT/audio/video HAL и не полноценный движок Tetris/SRS. Без звука, сохранений, ghost piece и lock delay.

## Как будет выглядеть первый запуск

1. Если ID экрана распознан по извлечённой таблице, профиль выбирается сразу. Если нет — последовательно показываются профили B/C/A примерно по 3 секунды. На читаемом экране `LCD SELECT` нажмите любую обычную кнопку, затем отпустите её. Интервал зависит от работоспособности таймера.
2. `KEY SETUP / RELEASE ALL`: отпустите все кнопки. По очереди назначьте **разные** кнопки для `LEFT`, `RIGHT`, `TURN`, `DOWN`, `DROP`, `PAUSE`. Держите нажатие до появления `RELEASE KEY`, затем отпускайте. Одновременные нажатия при обучении отклоняются; повторное назначение той же кнопки показывает `OTHER KEY`.
3. После шестой кнопки и её отпускания начинается игра. `PAUSE` включает/снимает паузу. После `OVER` нажмите `DROP` или `PAUSE` для новой игры.
4. После каждого перезапуска назначение выполняется заново. Оно не записывается во флеш. Во время обучения не удерживайте клавиши заранее; кнопку питания лучше не назначать.

Экранные подписи ASCII: в маленьком встроенном шрифте нет кириллицы.

`preview.png` и `calibration.png` — изображения, полученные **из framebuffer настоящего скомпилированного ARM-кода в эмуляторе**, не фотографии телефона. Игровая картинка — специально подготовленное демонстрационное состояние поля.

## Образ и память

| Параметр | Значение |
|---|---|
| Образ | `build/kenshi_tetris_maui.bin`, только замена MAUI |
| Размер | 13184 байт (`0x3380`) |
| Логический интервал NOR | `[0x00B000, 0xe380)` |
| Load / entry | `0x1000B000` / `0x1000B5B0` |
| GFH | сохранён board-template исходного дампа, content/jump=`0x5B0`, signature=0 |
| Векторы | первые `0x100` PSRAM зарезервированы, копируется `0x40` байт |
| DMA-резерв | `[0x100, 0x2100)`, 8 КиБ; реального DMA в этой игре нет |
| Framebuffer | `[0x2100, 0xC100)`, 40 КиБ, CPU через `0xF0002100` |
| Тень кадра, игра, управление | `.bss`, в PSRAM |
| Непрерывный heap | `[0x16240, 0x400000)`, 4103616 байт, около 3.91 МиБ |
| ARM-стеки | TCM, выравнивание SP перед вызовами C99 — 8 байт |

Код выполняется XIP из NOR. Внутренняя SRAM/TCM остаётся под cache/стеки/mailbox, framebuffer и тень — в PSRAM. Linker содержит `ASSERT((__heap_end - __heap_start) >= 0x200000, ...)`. Размер области гарантирован **линкером при принятой карте 4 МиБ PSRAM**, но её реальное наличие на данном телефоне ещё не доказано. В тестовой игре `malloc` не используется и allocator не реализован: область под него только зарезервирована. Суммарный `bss` в выводе `size` включает NOLOAD-резерв heap, это не объём занятых игровых данных.

SHA-256 образа:

```
c34a5281d724d2b7f97ce48182d14fafda9603da3bc6e78aa3f75699f71a8b91
```

## Важное: не записывать вслепую

**Архив не содержит команды записи/стирания или автоматического доступа к телефону.** `flash-plan.json` — описание логических границ, а не разрешение на запись.

- Подписанные ARM_BL/ARM_EXT_BL, область `[0, 0xB000)` и системный хвост `[0x389000, 0x400000)` должны сохраняться.
- Если инструмент стирает 64-КиБ блоками, начало `0xB000` находится в одном блоке с загрузчиками `[0, 0x10000)`. Даже маленький файл с правильным offset тогда может уничтожить загрузчик. Для 32-КиБ блока также возможно пересечение с защищёнными данными.
- Нужны фактический JEDEC/геометрия NOR, проверенный поддерживаемый способ записи без затрагивания защищённых диапазонов и способ восстановления. Если инструмент не умеет безопасно выполнить эту запись, остановиться, а не стирать весь первый блок.
- Нельзя считать собранный GFH доказательством принятия нового образа штатным BL2: сохранённые вспомогательные записи содержат старые opaque board-метаданные, их семантика при замене MAUI ещё не проверена.
- Последнее наблюдение Windows: `MINI_2`, `VID_0E8D&PID_0002`, служба `USBSTOR`. Это обнаруженный USB-накопитель; успешный сеанс штатного download/programmer-протокола не установлен.

## Аппаратные допущения и отличия от шага 2

1. LCD-профили взяты из того же предоставленного NOR, но установленная панель, тайминги, ориентация и реальная цветопередача пока не подтверждены. PIO синхронный: в момент передачи кадра клавиатура не опрашивается; реальный FPS не измерен. Отдельная инициализация подсветки/PMIC не изобреталась, возможна зависимость от состояния после BL2.
2. В **этой отдельной версии** исправлено включение тактирования LCD/SLCD: снятие bits0/7 power-down через 16-битный `PDN_CLR0` (`0xA0010320`), а не SET (`0xA0010310`) из прежнего кандидата. Это следует из справочных определений MT6261 PCTL, но не заменяет измерение на плате. Старый проект не исправлялся/не перезаписывался.
3. GPT4: свободно бегущий 32-битный счётчик `0xA00C002C`, включение через `0xA00C0028`, предполагается 26 МГц; clock gate GPT снимается через `0xA0010328` bit2. IRQ и PLL не настраиваются, ранее сброшенный LOCK не устанавливается. Обработаны дробные миллисекунды и переполнение. Источник: имеющийся справочник регистров MT6261D и определения PCTL, а не новая трассировка частоты на этой плате.
4. Если GPT4 не меняется при начальной проверке, есть явный приблизительный программный fallback с надписью `SOFT`. В нём скорость игры/обучения зависит от задержек и PIO, точное реальное время не гарантируется.
5. EMI/PLL/питание наследуются от BL2. Cache/remap/MPU, PSRAM alias и keypad-параметры перенесены из кандидата шага 2; на телефоне они ещё не проверены. Полный PSRAM-тест может остановить запуск до игры; при отказе возможен красно-белый экран ошибки из прежней диагностики, при раннем отказе cache — остановка без изображения.
6. Прошивка не перезаписывает собственный NOR и не хранит раскладку/счёт. Нет подтверждения автономного старта, удержания питания PMIC и потребления после отказа от MAUI.

## Структура и сборка

```
src/startup.S, boot.c, board.c, psram.c  — старт/память/bring-up
src/lcd.c, lcd_profiles.inc, font.inc  — LCD/шрифт/dirty-row PIO
src/tetris.c                         — независимая C99-логика игры
src/input.c                          — обучение и чтение действий
src/clock.c, ui.c, main.c             — время/экран/главный цикл
linker/mt6261.ld                      — карта и ASSERT
board/lcd_profiles.json              — source-tagged команды из NOR
tools/                               — GFH, генерация, сборка, проверки
tests/                               — упаковка и ARM-эмуляционные проверки
```

Нужны Python 3, `arm-none-eabi-gcc`/binutils, GNU Make. Проверено Arm GNU Toolchain 14.2.Rel1 (GCC 14.2.1), `-march=armv5te -marm -mfloat-abi=soft`, C99, `-Wall -Wextra -Werror`, без libc. Toolchain и Python-пакеты в архив не включены. Исходный NOR читается для повторного извлечения и проверки GFH; путь по умолчанию соответствует пути пользователя.

Из корня проекта:

```powershell
make check "DUMP=C:/MTK_Drivers/dump_tool/kenshi_mini2_full.bin"
make check-heap
# Для ARM-эмуляционных проверок нужны зависимости requirements-test.txt:
make check-emu check-game
```

Если GNU Make отсутствует:

```powershell
python tools/build.py --prefix arm-none-eabi- --dump C:/MTK_Drivers/dump_tool/kenshi_mini2_full.bin
# Это сборка и базовые проверки; дополнительные проверки отдельно:
python tools/check_heap_assert.py --prefix arm-none-eabi-
python tests/emulate_psram.py
python tests/emulate_startup.py
python tests/emulate_game.py --prefix arm-none-eabi-
```

## Что действительно проверено

- Сборка и базовые проверки пройдены как Python-builder, так и GNU Make.
- 11 unit-тестов GFH/границ/шаблона. Проверены entry, наличие ARM-инструкции в начале, длина payload и SHA-256.
- Heap ASSERT: **полный набор игровых объектов**, положительный контроль с добавлением 1 МиБ `.bss` проходит линковку; с добавлением 2 МиБ линковка отклонена требуемым ASSERT, без undefined references.
- Стартовый ARM-код в Unicorn: первая MMIO-запись WDT, banked stacks, копирование векторов/data, очистка bss, переход к main; cache command auto-clear и alias специально моделируются.
- PSRAM-тест в моделях: 4 МиБ без зеркала принимаются; меньшие зеркальные модели и неисправный бит отвергаются. Это не измерение физической PSRAM телефона.
- C99-логика игры/обучения: 304597 проверок, включая повторяющиеся проверки внутри stress-прогона на 1500 шагов. Формы, стены, повороты, падение, линии, pause/restart, canary-границы, debounce, отпускание/дубликаты и переполнение времени.
- Реальный ARM UI сформировал preview. Проверен поток 40960 байт пикселей полного кадра, отсутствие передач при неизменном кадре, точное окно/порядок байт при смене одного пикселя, clipping прямоугольников и экраны назначения кнопок.
- GPT4-модель: дробные миллисекунды, wrap, fallback. Проверены адрес/ширина gate-записи LCD и соответствие ID профилям.

Все эти аппаратные обращения проверялись **на модели хранения регистров**, не на реальном контроллере/шине. Отчёты — `build/*-emulation.json`, `build/heap-assert-test.json`, `build/verified-layout.json`; это не обещание готовности к безопасной прошивке.
