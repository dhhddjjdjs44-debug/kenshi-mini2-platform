# Kenshi Mini 2 / The Night Shift — шаг 1: статический анализ NOR

**Дата:** 16 ноября 2026 года.  
**Статус:** подготовлен статический отчёт; аппаратная валидация не выполнялась. Шаги 2–3 не начаты.  
**Изменения:** исходный образ и отслеживаемые файлы `dump_tool` не изменялись. Созданы только аналитические материалы в рабочем каталоге этого чата. Не выполнялись прошивка, подключение к загрузчику телефона, запись регистров или запуск кода на устройстве.

## 1. Объект исследования и границы доказательств

Образ: `C:\MTK_Drivers\dump_tool\kenshi_mini2_full.bin`  
Размер: **4 194 304 байта = 0x400000 = 4 МиБ NOR**. Это размер файла, а не измерение RAM.

SHA-256 до и после анализа:

```text
9109aa340956f2da8cd981b4501c1803d14f097b331709cc7187c6ff2005fafc
```

Исследование: заголовки little-endian, GFH/FILE_INFO, печатные строки, ARM/Thumb-дизассемблирование Capstone 5.0.9, literal pools и перекрёстные ссылки, стартовые копирования/обнуления памяти, статическое восстановление LCD-последовательностей. Дизассемблер установлен изолированно в `work/pydeps`, не в репозиторий пользователя.

Обозначения уверенности:

- **D — непосредственно из дампа:** байты, размер, регистровые операции, инструкции и адресные ссылки.
- **I — статическая интерпретация:** смысл подтверждается несколькими участками кода и/или первичными техническими материалами, но не измерен на плате.
- **R — внешняя справка:** полезна для сопоставления; не доказывает ревизию и распайку Kenshi.
- **H — требует устройства:** фактический объём и надёжность RAM, выбранный LCD-профиль, pinmux, клавишная матрица, рабочая аудиотрасса, доступ DMA к TCM.

Аналитические имена функций в этом отчёте — не восстановленные отладочные символы. Все интервалы ниже **с исключённой правой границей**. Смещение в файле нельзя смешивать с адресом CPU.

В прошивке найдены строки:

- `M02_128X160_SK_F193_1_PCB01_gprs_MT6261_S00.MINI_2_C1_250528.bin` — file `0xB040`;
- `MT6261PRO` — file `0x149D8`, `MT6261` — file `0x1D834`;
- Nucleus PLUS ARM 7/9 `1.11.19` — file `0x6D285`;
- build-строка у `0x172C5C`, содержащая `2025/07/28 17:39`.

Это идентификаторы содержимого образа, не независимая идентификация корпуса кристалла. Полный NOR не содержит автоматически весь mask BootROM и актуальное содержимое RAM. Папка `dump_tool` содержит инструментарий MTK; исходники The Night Shift по указанному пути не предоставлены.

## 2. Структура загрузочного образа и карта NOR

### 2.1. Верхний уровень

| Смещения в файле | Назначение | Основание |
|---|---|---|
| `0x000000–0x000200` | Заголовок serial flash boot | `SF_BOOT` в `0x0`, поле размера единицы `0x200` в `0x10` — D |
| `0x000200–0x000800` | Область BRLYT и заполнение | `BRLYT`, версия 1, дескрипторы `BBBB` — D |
| `0x000800–0x0026AC` | ARM_BL, первый загрузочный компонент | FILE_INFO: type `0x0001`, length `0x1EAC` — D |
| `0x002800–0x00A248` | ARM_EXT_BL, второй компонент | type `0x0002`, length `0x7A48` — D |
| `0x00B000–0x0A28B0` | Основная часть MAUI | type `0x0100`, length `0x978B0` — D |
| `0x0A28B0–0x0A2CB0` | Промежуток между компонентами | Не отдельный найденный раздел |
| `0x0A2CB0–0x2977B4` | Дополнительная часть MAUI, сжатые/пакетированные данные | type `0x0108`, length `0x1F4B04` — D; точная семантика всех внутренних блоков не восстановлена |
| `0x2977B4–0x389000` | Полностью заполнено `0xFF` | Проверены **все** 989 260 байт — D |
| `0x389000–0x400000` | Непустой системный хвост | 487 424 байта, не всё `0xFF`; есть служебные структуры — D; точное разбиение FS/NVRAM/метаданных пока I/H |

Промежутки между указанными загрузочными компонентами не объявляются новыми разделами. BRLYT не является полной Android-подобной таблицей разделов и не описывает microSD.

В MAUI присутствуют GFH типов `0x0200`, `0x0207`, `0x020E`, `0x020F`, `0x0102`, `0x0103`. Внутренние таблицы поддерживают несколько flash-конфигураций; наличие JEDEC ID в таблице поддержки не означает, что именно такой чип установлен.

### 2.2. Адреса загрузки и входа

| Компонент | FILE_INFO | Load address | Content / jump offset | Старт содержимого в файле | Адрес входа по заголовку |
|---|---|---|---|---|---|
| ARM_BL | `0x800` | `0x70006000` | `0x140` / `0x140` | `0x940` | `0x70006140` |
| ARM_EXT_BL | `0x2800` | `0x10002800` | `0x60` / `0x60` | `0x2860` | `0x10002860` |
| MAUI | `0xB000` | `0x1000B000` | `0x5B0` / `0x5B0` | `0xB5B0` | `0x1000B5B0` |
| MAUI type `0x0108` | `0xA2CB0` | `0x100A2CB0` | `0x38` / `0x0` | `0xA2CE8` | **Не считать самостоятельной точкой запуска** |

Для ARM_BL преобразование в его загруженную SRAM-копию: `CPU_VA = file_offset + 0x70005800`. Для исследованного NOR/XIP-окна: `CPU_VA = file_offset + 0x10000000`. Это две разные схемы.

Первый переход ARM_BL в file `0x940` ведёт к `0x70006194`; второй стартует ARM-кодом в `0x10002860`, затем `0x1000288C` и Thumb `0x100028BC`. MAUI содержит ARM-векторы в `0x1000B5B0`; reset-вектор читает адрес **`0x1000B670`**, а не ошибочно выбранный участок literal pool.

Перед передачей управления второй загрузчик печатает строку из file `0x908C`, условно записывает `3` в 16-битный регистр `0xA0510000` (file `0x9072–0x9076`), а затем вызывает ARM veneer `0x10009F3C`, содержащий `BX r0`. Адрес берётся из ранее проверенного компонента; эта находка **не является готовым патчем или инструкцией прошивки**.

Поля signature type/length прочитаны, но криптографическая корректность, политика доверия BootROM и допустимость изменённого образа **не проверялись**. Наличие заголовка не означает, что любую замену примет устройство.

### 2.3. Сжатые области

- В `0xA2CE8` есть внутренние адресные поля, среди которых `0x100A2CFC`, `0x10172C14`, `0x101930C0`.
- В file `0x172C14` — `DCMGBODY`.
- В file `0x1930C0` — **`ALICE_2`**.
- Отдельные LZMA-alone потоки действительно декодируются, например с file `0x845D4` и `0x92310`. Это **не доказывает**, что весь основной упакованный компонент является обычным LZMA-alone.
- Попытка стандартного LZMA-alone декодирования кандидата у `0xA2D14` завершилась ошибкой. Полная реконструкция логического адресного пространства сжатой части не выполнена.

В существующей папке `unpacked` обнаружены ранее созданные производные файлы. `alice_original_component.bin` побайтно совпадает с соответствующим отрезком исходного NOR. Происхождение/алгоритм преобразования `alice-py.bin` и `alice-translated-py.bin` не верифицированы; они **не использованы как доказательство правильного кода** и не изменялись.

## 3. Карта RAM, алиасы и действующая конфигурация MPU

### 3.1. Восстановленная адресация

| CPU-диапазон | Размер | Вывод |
|---|---:|---|
| `0x00000000–0x00400000` | `0x400000` | Основное RAM-окно, под которое настроен стартовый код — D/I. Физическая ёмкость и отсутствие зеркалирования требуют теста H |
| `0xF0000000–0xF0400000` | те же 4 МиБ | Некэшируемый remap-алиас RAM. **Не дополнительные 4 МиБ** — D/I |
| `0x10000000–0x10400000` | `0x400000` | NOR-окно в исследованной конфигурации — D/I |
| Область `0x70000000` | верхняя граница по дампу не доказана | Внутренняя SRAM/TCM и загрузочные данные — D/I |
| `0x70000000–0x7000B000` | `0xB000` = 44 КиБ | **Внешний ориентир R** из открытого MT6261A-проекта; не измеренная ёмкость этой платы |

Стартовая процедура `0x1000C2FC` передаёт в `0x1000CA00`:

```text
physical_start = 0x00000000
alias_start    = 0xF0000000
length         = 0x00400000
```

Функция записывает пары remap-регистров начиная с `0xA0531000`. Для этой конфигурации статически получается первая пара: `HI0 = 0xF000001B`, `LO0 = 0x00000000`. Это вычисление по инструкциям и параметрам, не live-read регистров.

Та же процедура пишет в MPU: `0x10000100` в `0xA0540000`, `0x10001000` в `0xA0540040`, затем устанавливает младший бит в `0xA053002C`. Политика всех MPU-каналов и их итоговое состояние после запуска RTOS не восстановлены. Эти значения нельзя механически переносить в новый HAL как законченный набор настроек.

Низкие векторы используются: MAUI копирует 0x40 байт векторов к адресу `0x0`. Следовательно, считать RAM начиная с нуля свободным heap без резервирования векторов нельзя.

### 3.2. Реальные размещения штатной прошивки

Подтверждены вызовы стартовых copy/zero-процедур; весь перечень сохранён в `memory_map.json`:

| Операция | Источник | Назначение | Размер |
|---|---|---|---:|
| Copy | `0x1009B8A4` | `0xF004EDC0` | `0x5424` |
| Zero | — | `0xF00541E4` | `0xF888C` |
| Copy | `0x100A0CC8` | `0xF014CA70` | `0xD24` |
| Zero | — | `0xF014D794` | `0x3DE0` |
| Zero | — | `0xF0152574` | `0xEE1DC` |
| Copy | `0x100A19F0` | `0x70008000` | `0x2EC` |
| Zero | — | `0x700082EC` | `0x294` |
| Copy | `0x100A28A0` | `0x70009308` | `0x8` |
| Zero | — | `0x70009310` | `0x978` |

Есть также отдельная инициализация участков `0x003EB000` размером `0x18F0` и `0x003F1000` размером `0x3B00`. В reset-коде используется стек `0x70009C74` и указатели на сохранённые данные у `0x70009C78`.

**Это карта потребления штатной прошивки, не карта свободной памяти для игры.** В перечне всех операций есть альтернативные фазы и перекрывающиеся SRAM-области; их нельзя суммировать как одновременно живущие секции. Сжатые/динамические области и runtime heap штатной системы разобраны не полностью.

### 3.3. EMI

В первом загрузчике найден GFH type `0x0101`, version 5: file `0x8C4`, length `0x4C`; строка `EMI_INF` расположена в `0x8D4`. В основной прошивке есть `hal\system\emi\src\emi.c` у `0xC72C`. Непосредственно перед этой строкой процедура `0x1000C708` состоит из `BX LR`: **это stub, а не найденная последовательность программирования таймингов PSRAM**.

Есть обращения к области `0xA0050000` (в частности `0xA0050180`, `0xA0050200`). Открытые материалы по родственному MT6260 относят её к EMI. Это полезная наводка, но не основание подставить register map/тайминги MT6260 в MT6261.

**Не восстановлено:** точный тип установленной RAM, полный набор таймингов EMI, зависимости от частот/питаний и все операции BootROM, выполнявшиеся до первого компонента NOR. Поэтому «инициализация EMI полностью извлечена» было бы неверным утверждением.

## 4. LCD: восстановлены функции и три профиля

### 4.1. Подтверждённые регистры и процедуры

LCDIF-base **`0xA0450000`** подтверждён инструкциями. Запись reset-control выполняется по `0xA0450010`.

| Аналитическое назначение | File offset / CPU address | Доказательство |
|---|---|---|
| Запись команды | `0x378B8` / `0x100378B8` | 16-битная запись аргумента в `0xA0450F80` |
| Запись данных | `0x378EC` / `0x100378EC` | 16-битная запись в `0xA0450F90` |
| Окно профиля C | `0x29A20` / `0x10029A20` | Команды `2A`, `2B`, `2C` с координатами |
| Окно профиля A | `0x29AB8` / `0x10029AB8` | Аналогичная отдельная процедура |
| Окно профиля B | `0x29B50` / `0x10029B50` | Аналогичная отдельная процедура |
| Привязка общего LCD API | `0x21EDC` / `0x10021EDC` | Указатель на таблицу `0xF0050A04` записывается в `0xF01049BC` |

16-битная CPU-запись в порт данных сама по себе не доказывает 16-битную физическую шину LCD. Нужны значения интерфейсной конфигурации и сведения о панели.

### 4.2. Профили инициализации

| Профиль | Init file offset / CPU address | ID-read | Характерные команды |
|---|---|---|---|
| A | `0x29CCC` / `0x10029CCC` | `0x1002CCF8` | `FF:A5`, `3E:08`, `3A:65`, многочисленные настройки, `FF:00`, `11`, `36:48`, `29` |
| B | `0x29FB4` / `0x10029FB4` | `0x1002CDC0` | `11`, `B1:05 3C 3C`, `B2`, `B3`, `C0…C5`, `36:C8`, `E0/E1`, `3A:05`, `29` |
| C | `0x2DF44` / `0x1002DF44` | `0x1002CC38` | `FE`, `FE`, `EF`, `B3:03`, `B6`, `21`, `36:D8`, `3A:05`, `F0/F1`, `FE`, `FF`, `11`, `29` |

Все три связаны таблицами function pointers около file `0x9D538–0x9D574`. Общий API обращается к выбранному профилю через runtime-указатель. ID-read-процедуры посылают `DA`, `DB`, `DC` и читают байты панели. По одному NOR без прослеживания всех ветвей выбора и/или чтения ID **нельзя честно назвать единственный установленный контроллер**. По сходству команд нельзя объявлять его ST7735, GC9106 или другим конкретным чипом.

Полная статическая последовательность каждого профиля с file-offset каждой операции — в `lcd_profiles_static.txt`. Сохранены reset-состояния и сырые аргументы задержек (`0x0A`, `0x32`, `0x78`, и др.). Время этих аргументов пока **не аттестовано в миллисекундах**: функция задержки опирается на таймер и расчёт elapsed-time, нужны частотные предпосылки.

В профилях A/C отдельно видны циклы очистки на 20 480 пикселей / 128×160; их DATA-записи не ошибочно приписаны параметрам последней команды `29`. Статическая выгрузка не выполняет и не разворачивает циклы.

**Ещё не доказано:** физическая модель панели, нужные смещения GRAM и ориентация, порядок байтов/BGR, фактические bus timings, возможность LCD/DMA читать полный framebuffer из TCM. Это обязательные проверки перед обещанием быстрого SRAM-blit.

## 5. Клавиатура

**Подтверждён блок KP `0xA00D0000`.** В file `0x1EF08–0x1EF1C` штатный код читает 16-битные регистры `+0x4`, `+0x8`, `+0xC`, `+0x10`, собирая два 32-битных слова состояния.

Сопоставление с первичным datasheet MT6261D, PDF pages 145–150:

- `KP_STA` — `0xA00D0000`;
- `KP_MEM1…5` — `0xA00D0004`, `08`, `0C`, `10`, `14`;
- `KP_DEBOUNCE` — `0xA00D0018`;
- `KP_SCAN_TIMING` — `0xA00D001C`;
- `KP_SEL` — `0xA00D0020`;
- `KP_EN` — `0xA00D0024`.

В datasheet состояние нажатия — active-low. В file `0x28D3C–0x28D68` есть keypad-related настройка GPIO и запись в `KP_EN`; это не полная восстановленная таблица инициализации. Нельзя взять один этот фрагмент и считать клавиатуру готовой.

**Не восстановлено:** привязка физических цифр/D-pad/softkeys к row/column, все pinmux-настройки, штатные значения scan/debounce и маршрутизация power-key. Ограничения одновременных нажатий зависят от матрицы; «без задержек» в будущем означает неблокирующий опрос и bounded debounce, а не физически нулевую задержку.

## 6. microSD / FAT32

**Подтверждён MSDC0-base `0xA0130000`.** Есть многочисленные обращения, включая code у file `0xF7A2`, `0x117A0–0x11800`, `0x11F0E`, `0x13DC4`, `0x147D0`. Названия по datasheet MT6261D, PDF pages 438 и далее:

| Регистр | CPU address |
|---|---|
| MSDC_CFG / STA / INT | `0xA0130000 / 04 / 08` |
| MSDC_PS | `0xA013000C` |
| MSDC_DAT (FIFO) | `0xA0130010` |
| MSDC_IOCON | `0xA0130014` |
| SDC_CFG | `0xA0130020` |
| SDC_CMD | `0xA0130024` |
| SDC_ARG | `0xA0130028` |
| SDC_STA | `0xA013002C` |
| SDC_RESP0 | `0xA0130030` |

**Ещё не извлечено полностью:** порядок питания слота, pinmux, card-detect, исходная частота и переключение ширины шины, корректные timeout/CRC/recovery и DMA-когерентность. На этом этапе сектор с карты не прочитан.

FAT32 — отдельный программный слой. Наличие SD-драйвера в прошивке не означает, что найден независимый callable FAT32 API без RTOS/MMI. FAT32 будущего HAL разумно держать отдельным модулем; выбор и подключение относятся к шагу 3. Форматирование карты или запись на неё не выполнялись.

## 7. Аудио и видео — граница текущего результата

В NOR присутствуют `L1Audio` (file `0x13844`), `hal\audio\src\v1\audio_service.c` (file `0x3066C`, `0x5C250`), строки очередей/HISR аудиоподсистемы. Это доказательство наличия штатной аудиоподсистемы, **не доказательство восстановления минимального PCM-ЦАП-драйвера**.

Открытый MT6261-проект содержит AFE/DPRAM-исходники и кандидат AFE-base `0x82CD0000`. Его прямое использование этой прошивкой не подтверждено; **адрес не внесён в карту как найденный DAC**. Нужны трассировка реально используемых функций, соответствие ревизии и схема маршрута PCM → буфер/DSP/AFE → аналоговый выход/усилитель. Нельзя заменять эту работу перечислением правдоподобных MMIO.

**Не восстановлены:** рабочие регистры/последовательность ЦАП, audio-DMA или DSP-буферы, IRQ, допустимые sample rate/канальность, аналоговые mute/gain/power и гарантированная доступность SRAM для этого пути. Удаление GSM-задач не означает, что можно выключить все общие DSP/clock/power-домены и сохранить звук.

PCM/WAV/IMA ADPCM-декодер и streaming video player пока не писались. Контейнер WAV не тождественен PCM: будущий parser должен проверять формат. MJPEG-производительность нельзя гарантировать по размеру экрана; нужны CPU/SD-декодирующие замеры. Для будущей синхронизации естественен счётчик фактически воспроизведённых аудиосэмплов, но проектирование плеера остаётся шагом 3.

## 8. Проверка жёсткого требования памяти: выявлены два ограничения

### 8.1. Нельзя пока принять «48–64 КиБ свободной SRAM»

Размер полного framebuffer: `128 × 160 × 2 = 40 960 = 0xA000` байт (**40 КиБ**).

Внешний MT6261A linker reference задаёт TCM `0x70000000`, length `0xB000` и описывает 12 КиБ общего использования + до 32 КиБ cache. Штатный дамп действительно использует данные/стеки начиная с `0x70008000`, что согласуется с такой границей 32 КиБ, но не доказывает физический предел кристалла.

Если применима конфигурация **44 КиБ всего**, то:

- при сохранении 32 КиБ cache остаётся лишь 12 КиБ SRAM: полный framebuffer туда не помещается;
- даже если все 44 КиБ доступны как RAM после отключения/repartition cache, `0xB000 − 0xA000 = 0x1000`: всего 4 КиБ на стеки ARM-режимов, векторы, audio/DMA и прочие горячие данные;
- CPU-доступ к TCM не является доказательством доступа LCD/audio DMA.

Поэтому обещать строго заданное пользователем размещение framebuffer + stack + audio в SRAM **сейчас нельзя**. Нужны точный вариант SoC, контроль кэша/TCM и тест доступности. Если предпосылка не подтвердится, потребуется согласовать изменение: полный framebuffer в PSRAM и небольшой SRAM line/tile-buffer либо другая схема. Самовольно такая замена не сделана.

### 8.2. Linker ASSERT не гарантирует свободную runtime-память

Для 4 МиБ RAM арифметический предел вне heap составляет:

- при минимуме heap `0x180000` — не более `0x280000` на всё остальное;
- при минимуме heap `0x200000` — не более `0x200000` на всё остальное.

Но размер секции heap, свободный объём allocator и **крупнейший свободный блок в процессе игры** — три разных свойства. `ASSERT` на этапе линковки проверит зарезервированный непрерывный диапазон, а не последствия malloc/free после запуска, не аппаратную ёмкость RAM и не ошибки EMI/DMA.

Если требуется постоянно свободный блок полезной ёмкости минимум `0x180000`, нужно отдельно учитывать allocator metadata/alignment, все игровые/медиа allocation peaks и фрагментацию либо резервировать недоступную прочим потребителям арену. Это необходимо согласовать до шага 2. Без исходников игры и измерений runtime-гарантия не дана.

## 9. Что необходимо закрыть до безопасного выбора архитектуры

Это список недостающих доказательств, **не выполненные аппаратные тесты**:

1. Точная маркировка/ревизия SoC/MCP, объём SRAM/TCM и режим cache. Тест физического RAM-окна на зеркалирование, ошибки и резервированные области должен проводиться только отдельной согласованной диагностикой, а не разрушать память действующей прошивки.
2. Live-состояние EMI/NCREMAP/MPU после загрузчика и реальные частоты. Показанные в отчёте значения — static reconstruction.
3. Какой из трёх LCD-профилей выбирается; чтение `DA/DB/DC`, корректность RGB565/окна/reset и достижимая скорость вывода.
4. Карта keypad row/column и отдельный маршрут power-key.
5. Чтение SD-секторов, питание/pinmux и поведение при timeout/removal.
6. Проверенный аудиопуть, IRQ, clock/power dependencies, SRAM/DMA compatibility. Это сейчас крупнейший нерешённый HAL-блок.
7. Путь к исходникам The Night Shift, размер `.text/.rodata/.data/.bss` и пиковое потребление игры/медиа.
8. Согласованный и проверяемый путь восстановления исходного телефона до любых операций записи. Системный хвост NOR и загрузочные данные пока нельзя объявлять мусором и стирать.

Статически bare-metal-вход через штатный проверенный формат MAUI представляется возможным направлением исследования. Однако **выбор и реализация архитектуры шага 2 не сделаны**: ещё не доказано, что к моменту передачи управления готова вся нужная периферия; наличие загрузчика не означает готовый LCD/SD/аудио HAL. Предложение «оставить загрузчик, удалить GSM» не равно байтовому удалению кусков связанной MAUI-прошивки.

## 10. Состав материалов и источники

Соседние файлы:

- `memory_map.json` — разобранные FILE_INFO, адресные окна, подтверждённые стартовые copy/zero-операции и ограничения;
- `static_disassembly_evidence.txt` — выбранные ARM/Thumb-фрагменты со смещениями, CPU-адресами и literal-pool annotations;
- `lcd_profiles_static.txt` — три извлечённых LCD-профиля; это анализ, не готовый драйвер.

Первичный источник всех специфичных для этой прошивки находок — исходный NOR с указанным SHA-256. Числовые факты воспроизводятся по указанным file offsets. Штатные пользовательские/уникальные данные из системного хвоста в отчёт не выгружались.

- **R1:** MediaTek, *MT6261D Data Sheet v0.4*, 496 PDF pages; keypad pp. 145–150, MSDC pp. 438 и далее. Это документ варианта **D**, не доказательство идентичности SRAM/периферии варианта на плате. Публичная копия находится в репозитории R2. Полный документ не включён в deliverables.
